## Goal

Complete the agent confirmation boundary on top of verified CB-122 local reference/evidence and
CB-118 commerce truth: arbitrate one exact confirmation, call commerce at most once for the
committed action, validate and atomically project the immutable ActionReceipt with the durable turn
result, and converge response loss, malformed responses, restart, and concurrent same-key replay
without a second commerce mutation.

## In scope

- Consume CB-122's shared total bounded parser, exact PendingAction reference, turn/event closure,
  and closed confirmation grammar. Only the documented exact positive forms for the current owned
  pending turn may enter confirmation arbitration; decline, expiry, and clarification remain
  CB-122 local decisions.
- Atomically claim an eligible local reference from `PENDING` to `CONFIRMING`, binding the durable
  confirmation turn and trace. The claim revalidates owner, support session, original prepare
  turn/trace, PendingAction identity, action/tool identity, canonical argument commitment, expiry,
  sandbox, and the absence of a conflicting local terminal decision.
- Acquire a fresh exact-scope OBO only after the claim is established, then call only the verified
  CB-118 confirm/result boundary with the stored PendingAction identity. Model output, client fields,
  and local prose cannot change owner, action, arguments, target/version, scope, session, turn,
  trace, sandbox, or idempotency.
- Treat every commerce response as untrusted. Use the shared bounded decoder and validate the
  complete receipt schema, unique keys, identity, owner/session/turn, action and argument
  commitment, authoritative result, sandbox, and authenticated source before local success.
- In one `cs_db` transaction persist exactly one immutable ActionReceipt projection, append exactly
  one `ACTION_RECEIPT` support event, transition the reference to `CONFIRMED`, and commit the same
  durable confirmation turn to the `action_completed` terminal outcome. None of those local success
  truths may exist without all the others.
- Make the successful commerce-owned ActionReceipt the authoritative turn-level commit point. The
  local transaction is its publication/replay checkpoint and may not redefine, undo, or repeat the
  commerce action.
- Resolve stored local receipt closure before any commerce request. For a durable `CONFIRMING`
  reference without a local projection, query the fixed CB-118 result boundary using the same
  identity and exact-scope authority; never re-prepare, change intent, or infer absence from a
  missing local row or failed observation.
- Converge same-key response loss, process restart, concurrent confirmation, local transaction
  rollback, and model/network failure to one projection, one receipt event, one confirmed reference,
  and one terminal turn. A valid local projection is receipt-first replay truth and suppresses any
  further commerce call.
- Maintain a closed executable inventory of every confirmation-reachable rejection and unavailable
  producer, including claim, OBO, commerce confirm/result, receipt parsing, recovery observation,
  durable-integrity, and local persistence. Each producer has one request-local server-only reason;
  public responses remain fixed and reveal neither the reason nor dependency detail.
- Emit exactly one public `action_receipt` from the stored projection, followed by optional bounded
  non-authoritative explanation prose and exactly one terminal SSE event. Explanation retry uses
  stored receipt truth and the existing shared attempt budget without re-entering commerce.
- Add only exact agent migration/grant/OpenAPI changes and focused/real integration evidence needed
  for confirmation state, immutable projection, event, turn commit, and recovery.

## Acceptance criteria

1. Only a validated exact positive form for the current owned CB-122 reference can claim
   confirmation. Wrong issuer/audience/type, owner, session, prepare turn/trace, confirmation
   turn/trace, pending id, commitment, scope, expiry, sandbox, or local state fails closed before a
   commerce confirm call.
2. Confirmation arbitration is atomic and one-way: exactly one caller may establish the durable
   `PENDING → CONFIRMING` claim and its confirmation turn/trace binding. Concurrent confirm,
   decline, and expiry cannot create split local truth or allow commerce to commit while the local
   reference is `DECLINED` or `EXPIRED`.
3. The confirm request uses only stored immutable reference values and a fresh exact-scope OBO.
   Client/model input cannot substitute identity, PendingAction id, action, arguments,
   target/version, owner, session, scope, sandbox, or idempotency.
4. Commerce confirm and result responses are fully bounded and validated as untrusted. Duplicate
   keys, unknown/missing/wrong-typed/deep/oversized fields, wrong owner/session/turn/action/
   commitment/sandbox, contradictory result, unauthenticated source, and dependency indeterminacy
   cannot create any local success truth.
5. One local transaction writes the immutable receipt projection, `ACTION_RECEIPT` event,
   `CONFIRMED` reference, and `action_completed` terminal turn together. Controlled failure at every
   write boundary leaves none of those success records visible.
6. The projection/event/reference/turn closure has exact cardinality and complete content binding to
   the authoritative commerce receipt and CB-122 reference. Missing, duplicate, cross-turn,
   stale-trace, reordered, mutable, or contradictory local truth fails closed and never triggers a
   second commerce mutation.
7. Receipt-first replay precedes mutable liveness, identity exchange, and commerce. Once the complete
   local closure exists, same-key replay returns/re-emits it without another OBO exchange or commerce
   call, even after response loss, restart, disconnect, or explanation failure.
8. A durable `CONFIRMING` reference without local receipt truth is indeterminate, not absent or
   failed. Recovery queries only the fixed CB-118 result boundary and converges a committed valid
   receipt into the same durable confirmation turn; unavailable or malformed result remains a fixed
   typed failure with zero local success truth and no second mutation.
9. The mandatory composed evidence passes exactly:
   persisted `CONFIRMING` → deep or malformed receipt response → fixed typed failure → zero
   projection/`ACTION_RECEIPT`/terminal success → same key obtains the valid committed receipt →
   the same durable confirmation turn converges → exactly one local closure and no second commerce
   mutation. Identity 503, pre-commerce failure, or a different key/turn cannot substitute.
10. Concurrent same-key confirmation and response-loss/restart interleavings converge to one
    commerce ActionReceipt and one complete local closure. Changed intent, receipt identity, or
    receipt content conflicts without another commerce mutation.
11. Public non-streaming and SSE output derives action status only from stored projection truth:
    exactly one `action_receipt`, then optional bounded token prose, then one terminal event. Token
    text cannot synthesize, replace, contradict, or be interpreted as receipt truth.
12. Every confirmation-reachable rejection or unavailable result has exact request-local producer
    attribution. A same-status identity, liveness, parser, commerce, recovery, or persistence
    producer cannot satisfy another producer's test, and the reason never enters the public body.
13. Exact grants permit only required `agent_app` DML in `cs_db`; the projection is immutable and
    support events append-only. `agent_app` cannot read or mutate commerce PendingAction,
    ActionReceipt, refund, payment, order, ledger, or Outbox tables.
14. CB-118 remains the indivisible commerce validation/consume/refund/receipt transaction, and
    CB-123 never redesigns payment truth, refund contention, commerce idempotency, or transaction
    ownership.
15. No new action type, generalized recovery scanner, memory/summary, handoff, export, web,
    observability, deployment, real-provider, scripted-drill, or measured performance behavior is
    introduced.

## Rejection paths

- Reject positive consent inferred from model output, booleans, broad natural-language matching, a
  stale or non-current turn, another owner/session/trace, changed argument commitment, or any value
  not bound by CB-122 durable truth.
- Reject confirmation without one atomic `CONFIRMING` claim, claim after decline/expiry, lock/order
  paths that permit confirm-versus-decline split truth, and any local success written before complete
  commerce receipt validation.
- Reject reuse of an old/broad OBO, caller-selected scope or identity, direct `commerce_db` access,
  re-prepare after indeterminate confirmation, and any second commerce mutation after a committed
  receipt may exist.
- Reject permissive receipt parsing, duplicate/unknown/missing/deep/oversized fields, partial identity
  or commitment checks, local receipt synthesis, and treating malformed or unavailable response as
  absence, business conflict, decline, expiry, or success.
- Reject projection without receipt event/reference/turn, event without projection, terminal success
  without complete closure, mutable overwrite, duplicate receipt/public event, and multiple terminal
  SSE outcomes.
- Reject recovery that changes key, turn, trace, action, or intent; uses identity failure as the
  deep-receipt witness; retries commerce confirm instead of querying the committed-result boundary;
  or performs a second mutation after response loss.
- Reject broad grants, cross-database joins, global recovery scans, CB-118 transaction redesign,
  payment/refund rewrites, and CB-130 or later work implemented early.

## Out of scope

- CB-122 parser, initial prepare/reference creation, clarification, decline, expiry, and pre-confirm
  event closure except for consuming their verified interfaces;
- commerce PendingAction validation/consume, refund mutation, and authoritative ActionReceipt
  persistence already owned by CB-118;
- redesign of CB-116 committed-payment truth, CB-117 refund contention recovery, CB-118 transaction
  semantics, or a global cross-service lock protocol;
- new sensitive actions, background/global action recovery scanning, settlement, chargeback, or
  provider integration;
- memory/summary packing, prompt/PII and output safety owned by CB-130;
- handoff, failure export, web, observability, deployment, scripted drills, and measured
  load/latency/quality.

## Required evidence

- deterministic grammar/authorization tests proving only exact current-reference confirmation can
  claim and every decline/expiry/clarification path remains CB-122 behavior with zero commerce
  confirm;
- real MySQL arbitration for confirmation versus confirmation/decline/expiry, with fixed lock order,
  transaction rollback, restart, and no commerce/local truth split;
- real exact-scope OBO and CB-118 integration for success, same-intent replay, changed intent,
  authorization rejection, sandbox rejection/unavailability, true dependency failure, and no second
  commerce mutation;
- strict bounded receipt-decoder tests for duplicate/unknown/missing/wrong-typed/deep/oversized
  content and every identity/commitment/source mismatch;
- executable request-level producer inventory and safe log-window assertions for claim, OBO,
  confirm/result, parsing, durable-integrity, recovery-observation, and local-persistence rejection,
  proving public bodies do not leak and one same-status producer cannot impersonate another;
- real `cs_db` rollback injection at every projection/event/reference/turn write, immutable
  uniqueness, complete bidirectional closure, conversation/evaluation agreement, and zero partial
  success truth;
- deterministic response-loss, process-restart, disconnect, concurrent same-key, and receipt-first
  replay evidence proving exactly one local closure and one public receipt event;
- the mandatory persisted-`CONFIRMING` malformed-receipt-to-valid-result composition using the same
  key and durable confirmation turn, with fixed typed failure, zero partial local success, later
  convergence, and proof that commerce mutation count remains one;
- streaming and non-streaming evidence for receipt-before-prose, one terminal event,
  non-authoritative token text, and explanation-only retry under the shared budget;
- exact migration/runtime grants and cross-database denial evidence;
- regressions proving CB-080/081/082, CB-116/117/118, and CB-122 contracts remain unchanged and no
  CB-130 or later capability was implemented;
- complete-diff self-review, fresh independent read-only review, final-head CI, the unique closeout
  `make ci`, and factual completion evidence.
