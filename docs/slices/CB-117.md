## Goal

Make every affected refund transaction physically time-bounded and recover from recognized MySQL
lock competition only after the original transaction has rolled back. A fresh bounded transaction
must produce one immutable, fully validated lifecycle truth or a typed indeterminate outcome; no
locking validation may occur after that transaction returns.

## In scope

- Introduce a neutral bounded-MySQL transaction executor that, on the transaction's actual JDBC
  session, saves `@@SESSION.innodb_lock_wait_timeout`, applies validated configuration, executes the
  work, and restores the prior policy in `finally`. Restoration failure is visible and cannot return
  a business result.
- Compose that executor through a refund-specific transaction boundary for direct refund,
  processing, success, failure, and reconciliation top-level transactions. Do not couple refund
  entries to payment-specific transaction metadata.
- Detect contention by walking the throwable cause chain to a MySQL `SQLException` whose vendor
  error is exactly 1205 or 1213. Resource/acquisition failure remains unavailable; unrelated
  programmer/configuration failure remains visible.
- Exit and roll back the original transaction before recovery. Re-observe only in a new bounded
  transaction; never catch 1205/1213 inside the failed callback and continue reading or writing.
- In that fresh transaction, perform every locking read and complete lifecycle/payment/refund
  validation needed to construct one immutable validated truth. No transaction-external
  `validateCompletedLifecycle` or equivalent locking read is allowed.
- For direct refund, replay complete durable truth, permit at most one final mutation after a
  successful locking observation confirms absence, or return a bounded HTTP 429 when truth remains
  indeterminate.
- For internal lifecycle and reconciliation callers, return an existing persistent result or a
  typed indeterminate result for the owning HTTP, Broker, or task boundary to map. Indeterminate
  observation is never a contradiction or terminal business decision.
- Preserve pooled-session policy, fixed lock acquisition order, current refund state machine,
  idempotency intent, payment/refund reconciliation, PendingAction non-consumption, and zero partial
  ledger/Outbox/receipt effects.

## Acceptance criteria

1. Direct refund and every top-level refund lifecycle/reconciliation transaction use the one
   refund-specific boundary composed over the neutral executor. No affected entry uses a naked
   transaction template or an unbounded row-lock wait.
2. The executor proves it is inside an active Spring transaction and changes the same physical JDBC
   session used by the work. Configuration is validated and is not borrowed from mock-payment
   settings or hard-coded for tests.
3. The prior session lock-wait value is restored before pool return on success, 1205, 1213, rollback,
   and unexpected failure. Restoration failure is a visible infrastructure failure, not replay,
   conflict, 429, or success.
4. Recognized 1205/1213 always abort the original transaction. Recovery begins only after rollback
   in a fresh bounded transaction, and all writes performed before the failure are absent.
5. One bounded recovery transaction performs the full locking read and validation and returns an
   immutable validated lifecycle truth. No caller performs a later locking validation on that
   detached result.
6. Direct same-intent refund replay returns the existing durable result. A successful locked
   confirmed-absence observation may authorize one final mutation; a second contention permits
   final observation but never a second final mutation.
7. Exhausted direct-refund observation returns the fixed bounded 429 schema with server-only
   indeterminate attribution. Durable intent/integrity conflict remains 409, concealment remains
   the existing 404 family, and true persistence unavailability remains 503.
8. Processing/success/failure/reconciliation contention returns a typed indeterminate outcome to
   its owning boundary. Reconciliation does not count observation failure as contradiction, and
   asynchronous owners do not ACK an uncertain terminal result.
9. Cause-chain classification admits only vendor errors 1205 and 1213. No recognized lock exception
   escapes as 500, and no broad Spring exception category turns resource failure or programming
   failure into contention.
10. Real competing transactions for direct refund, lifecycle, and reconciliation finish within a
    documented finite bound for both 1205 and 1213, with no partial refund, ledger, Outbox, consumed
    PendingAction, or duplicate ActionReceipt.
11. The direct-refund OpenAPI includes the exact current public status set and bounded 429 error
    schema without SQL, lock, table, retry, or server-only reason detail.
12. No PendingAction/ActionReceipt implementation, global payment lock context, acyclic lock
    protocol, refund state-machine redesign, new table/index responsibility, or public success
    semantic change is introduced.

## Rejection paths

- Reject controller-only lock handlers, extra sleeps/retries, framework transaction timeout as a
  physical MySQL row-lock bound, wide `DataAccessException` contention classification, or raw
  1205/1213 escape.
- Reject catch-and-continue inside the failed transaction, re-observation before rollback, reuse of
  the failed transaction/session, transaction-external locking validation, or a mutable detached
  lifecycle snapshot.
- Reject direct refund depending on payment-specific transaction entry metadata or
  `citybuddy.mock-payment.*` configuration.
- Reject an indeterminate observation classified as absence, concealment, conflict, contradiction,
  success, dependency unavailability, or terminal asynchronous acknowledgement.
- Reject session-policy leakage, swallowed restoration failure, default lock-wait use on one entry,
  reversed lock acquisition order, partial writes, double mutation, or a retry that consumes
  PendingAction/creates ActionReceipt.
- Reject expanding into PendingAction schema/semantics, global lock redesign, new migrations,
  payment-provider behavior, settlement, chargeback, or later-slice work.

## Out of scope

- committed-payment face and public-visibility closure owned by CB-116;
- PendingAction, confirmation transaction, refund action consume, and ActionReceipt owned by CB-118;
- a global acyclic lock protocol or PaymentLockContext, lock-contention-rate optimization, refund
  state-machine redesign, provider settlement, and chargeback;
- agent confirmation/projection, memory, handoff, export, web, observability, deployment,
  real-provider access, and measured performance.

## Required evidence

- executable transaction-entry inventory for direct refund, processing, success, failure, and
  reconciliation, including executor, lock order, mutation/observation role, allowed root causes,
  result types, external classification, and write permission;
- deterministic unit evidence for cause-chain 1205/1213 classification, replay, confirmed absence,
  one final mutation, final observation, typed indeterminate, resource unavailability, unexpected
  failure, and restoration failure;
- real MySQL two-transaction 1205 and 1213 interleavings for direct refund, lifecycle, and
  reconciliation, proving bounded completion, full rollback, fresh-transaction observation, and no
  transaction-external locking validation;
- single-connection or otherwise identity-proven pooled-session evidence that captures the original
  session value, triggers contention, and observes the restored value as the next borrower;
- zero-effect evidence across refund, ledger, Outbox, PendingAction, and ActionReceipt plus same-
  intent replay and internal typed-retry evidence;
- direct-refund OpenAPI/status-set contract tests and server-only attribution tests;
- regressions for CB-071 refund/reconciliation and CB-116 truth/visibility contracts;
- complete-diff self-review, fresh independent read-only review, final-head CI, the unique closeout
  `make ci`, and factual completion evidence.
