## Goal

Close the pre-confirmation agent boundary for a commerce-owned PendingAction: parse action data
through one total bounded decoder, validate the authenticated CB-118 preparation result, persist one
owner/session/turn/trace-bound local reference with complete event evidence, and resolve
clarification, decline, and expiry without executing commerce confirmation. Exact confirmation
remains deliberately unavailable until CB-123.

## In scope

- Introduce one shared total, bounded action JSON parser used by both conversation and
  evaluation-evidence paths. It rejects duplicate object keys, unknown or missing fields,
  malformed Unicode or numbers, invalid nesting, and bytes/items/depth beyond fixed limits before
  materializing an unbounded object.
- Call only the verified CB-118 prepare boundary with a fresh exact-scope OBO after direct-user,
  support-session, turn, trace, owner, and evaluation-sandbox context has been established. Treat
  every commerce field as untrusted and validate the complete `PREPARED` response, PendingAction
  identity, action type, owner/session/turn/trace, canonical argument commitment, target/version,
  expiry, and sandbox binding.
- Consume the owner-approved CB-118 internal response amendment that projects the already durable
  owner, session, turn, trace, scope, sandbox, and target-version bindings. Compare those values
  against Agent-owned context, persist target version only as non-authoritative local evidence, and
  expose none of the added bindings to model, chat, or SSE output.
- Persist one agent-owned PendingAction reference in `cs_db`, bound to the server-owned support
  session, principal, preparation turn and trace, fixed tool identity, canonical argument
  commitment, commerce PendingAction id, expiry, and sandbox where applicable. The reference is a
  local orchestration/evidence record and never overrides `commerce_db` action truth.
- Persist the preparation turn as `action_pending` and append exactly one `ACTION_PREPARED` support
  event in the same local transaction as the reference. Replays resolve the complete durable local
  closure first. When no local closure exists because the authenticated CB-118 prepare response was
  lost or indeterminate, recovery may make only a bounded same-intent replay to that fixed
  idempotent prepare boundary with the original key and commitment; it cannot create a new intent,
  PendingAction, or business mutation.
- Apply one closed deterministic user-input grammar to the exact current reference. Ambiguous or
  unrelated text produces a bounded clarification without state transition or commerce call.
  Documented decline forms atomically transition the reference and owning turn to the fixed declined
  result and append the exact decline/terminal evidence. Expiry follows the same bounded local
  decision path after the recorded deadline.
- Define one shared conversation/evaluation action-event resolver for every action event introduced
  in this slice. Enumerate by stable session/turn relations before validating content, then require
  exact cardinality and full binding of event sequence, type, payload, owner subject, session,
  owning turn, owning turn trace, PendingAction identity, argument commitment, expiry, and sandbox.
  The same resolver must reject identical durable damage in conversation replay and evaluation
  evidence.
- Preserve CB-080 turn/event ordering, CB-081 ToolSpec/OBO/attempt-budget authority, CB-082 filtered
  SSE and non-authoritative prose, and CB-118 commerce truth. Decline, expiry, clarification, and
  replay never call commerce confirm and never create a local or commerce ActionReceipt.
- Give every action-reachable parsing, authorization/liveness, commerce preparation,
  durable-integrity, local-persistence, and deliberately unavailable confirmation producer a closed
  request-local server-only reason. Public status and bounded body remain the owning contract and
  never expose the internal reason or dependency detail.
- Add only the exact agent migration, runtime grants, OpenAPI surface, and focused/real integration
  evidence required for the reference, local decision, and event families.
- Return a fixed, bounded, typed non-success for an exact positive confirmation. That path performs
  zero OBO exchange for confirmation, zero commerce confirm/result call, and zero local state/event
  change; it cannot impersonate the confirmation capability reserved for CB-123.

## Acceptance criteria

1. The shared parser is a total function over every accepted input byte sequence within its declared
   bound and returns either one closed canonical action value or one fixed rejection. Bounds apply
   before collection/materialization, and no parsing exception or malformed persistent value escapes
   as 500, authorization, absence, or success.
2. Preparation uses only a validated direct principal, owned support session, server-owned turn and
   trace, fixed ToolSpec, and fresh exact-scope OBO. Wrong issuer/audience/type, owner, session, turn,
   trace, scope, sandbox, or liveness rejects before local reference persistence.
3. The CB-118 `PREPARED` response is fully validated as untrusted input. Duplicate/unknown/missing
   fields, wrong type or bound, identity/commitment/expiry/target mismatch, malformed response, and
   dependency indeterminacy cannot create an agent reference or pending event.
   Owner/session/turn/trace/scope/sandbox bindings come from the durable Commerce response rather
   than request echo, while `target_version` remains an immutable Agent evidence copy rather than
   action truth.
4. One canonical prepare intent produces exactly one reference, one `action_pending` turn, and one
   `ACTION_PREPARED` event. When that local closure exists, exact replay returns it without another
   commerce prepare. If the CB-118 prepare response was lost before local persistence, bounded
   replay of the original fixed prepare request must return the same commerce PendingAction before
   the one local closure is written. Changed action, argument, owner, session, turn, trace, target,
   version, expiry, sandbox, or idempotency conflicts without another row.
5. Every persisted action event is bound to exactly one owning turn, and its `turn_id`, `trace_id`,
   session, owner, sequence, type, payload, PendingAction id, argument commitment, expiry, and sandbox
   all match that turn and reference. Missing, duplicate, cross-turn, stale-trace, reordered,
   malformed, or contradictory event/reference/turn truth fails closed identically in conversation
   and evaluation paths.
6. Clarification changes no durable action state and calls no commerce action endpoint. A valid
   decline atomically records the fixed local declined state, exactly one `ACTION_DECLINED` event,
   and one terminal turn outcome. Expiry atomically records the fixed expired state and exact expiry
   evidence. Controlled failure at every local write point rolls back the entire local decision.
7. Decline/expiry replay is exact and side-effect free. It neither re-prepares nor confirms commerce,
   never creates a receipt projection or `ACTION_RECEIPT`, and cannot produce two terminal events.
8. Exact positive confirmation returns the documented fixed bounded non-success and performs zero
   confirmation OBO exchange, zero commerce confirm/result request, zero state transition, and zero
   event/receipt/terminal-success write.
9. Public streaming and non-streaming output retains the CB-082 filter: action status is not inferred
   from token prose, clarification/decline/expiry has one bounded outcome and one terminal event, and
   no synthetic `action_receipt` can appear.
10. Each action-reachable rejection or unavailable path records its exact request-local producer.
    A same-status producer cannot satisfy another producer's test, generic historical logs are not
    attribution, and public response bodies contain no reason, SQL, grant, liveness, or persistence
    detail. OBO 401/403 and Commerce validation/authentication/authorization/not-found,
    intent-conflict/durable-integrity, timeout/indeterminate/unavailable, and malformed-response
    producers remain distinct.
11. Exact runtime grants permit only the required `agent_app` DML in `cs_db`. Immutable support
    events remain append-only; unrelated columns/tables, DDL, deletes, and every `commerce_db` action,
    receipt, refund, payment, and order table remain denied.
12. Restart, repeated request, and client response loss after local commit converge from the stored
    reference/turn/event closure without another commerce prepare. CB-118 prepare response loss
    before local commit converges only through bounded same-intent replay of the fixed prepare
    boundary. Both windows produce one commerce PendingAction, one local closure, and zero commerce
    business mutation; neither permits a changed-intent replay.
13. No `CONFIRMING`/`CONFIRMED` local state, commerce confirm/result call, ActionReceipt projection,
    `ACTION_RECEIPT`, `action_completed` outcome, post-commerce recovery, memory, handoff, export,
    web, observability, or performance behavior is introduced.

## Rejection paths

- Reject unbounded or permissive JSON parsing, duplicate keys, unknown fields, late bounds, parsing
  exceptions, client/model-selected identity, and separate conversation/evaluation decoders with
  different acceptance.
- Reject preparation from a forged/cross-owner session, wrong turn/trace, wrong token mode/scope,
  altered ToolSpec or arguments, sandbox mismatch/inactivity/indeterminacy, and any body-supplied
  owner or authority.
- Reject trusting commerce `PREPARED` content without complete schema, identity, commitment, target,
  expiry, and sandbox checks; reject partial local persistence after malformed or unavailable
  commerce responses.
- Reject another prepare call after a complete local closure, changed-intent recovery after a lost
  prepare response, an unbounded prepare replay loop, and evidence that substitutes client response
  loss after local commit for the cross-service pre-local-commit response-loss window.
- Reject event lookup that filters on mutable validity fields, accepts a matching type with the
  wrong owning trace, validates payload without cardinality, or lets conversation and evaluation
  disagree on the same durable rows.
- Reject decline or expiry that leaves reference, turn, and events partially committed; repeated
  terminal events; local receipt synthesis; and any commerce confirm/refund/receipt effect from a
  local non-confirmation decision.
- Reject treating exact confirmation as success, clarification, decline, expiry, or a hidden
  commerce call. The fixed CB-122 confirmation response must remain non-success with zero effects.
- Reject broad grants, cross-database reads, mutable support-event updates/deletes, generalized
  recovery scanners, confirmation/receipt work, and CB-130 or later behavior implemented early.

## Out of scope

- exact confirmation arbitration, `PENDING → CONFIRMING/CONFIRMED`, confirmation OBO exchange,
  commerce confirm/result, ActionReceipt validation/projection, `ACTION_RECEIPT`, `action_completed`,
  and post-commerce recovery owned by CB-123;
- commerce PendingAction validation/consume, refund mutation, and authoritative ActionReceipt truth
  already owned by CB-118;
- redesign of CB-116 payment truth or CB-117 refund recovery, new action types, global recovery
  scanning, or a cross-service lock protocol;
- memory/summary packing, prompt/PII and tiered output safety owned by CB-130;
- handoff, failure export, web, observability, deployment, real-provider access, scripted drills, and
  measured load/latency/quality.

## Required evidence

- executable shared-parser tests for every accepted form and bounded malformed, duplicate-key,
  unknown-field, depth/item/byte, Unicode, number, and exception boundary;
- real authenticated CB-118 prepare integration proving exact-scope OBO, complete untrusted-response
  validation, local-closure-first replay, changed-intent rejection, dependency failure, and sandbox
  enforcement; separately inject CB-118 response loss after commerce commit but before local
  persistence, then prove bounded same-intent replay returns the original PendingAction and produces
  one local closure without another PendingAction or business mutation;
- real MySQL evidence for reference/turn/`ACTION_PREPARED` atomicity, exact cardinality and
  commitments, rollback at every local write point, restart, client response loss after local commit,
  and concurrent same-key replay;
- executable producer inventory and request-local log evidence for every action-reachable parser,
  authorization/liveness, prepare, durable-integrity, persistence, and unavailable-confirmation
  rejection, proving same-status paths cannot impersonate one another and public bodies do not leak;
- one shared conversation/evaluation closure matrix that corrupts each event/reference/turn
  identity and content binding, including the PR #64 cross-caller `trace_id` counterexample, and
  proves both callers reject the same durable damage;
- deterministic clarification, decline, and expiry tests proving exact local transitions, event
  order, one terminal outcome, replay convergence, SSE filtering, and zero commerce confirm,
  refund, ActionReceipt, local projection, or `ACTION_RECEIPT` effect;
- an exact-confirmation rejection test proving the fixed bounded non-success and zero confirmation
  OBO/commerce/local effects;
- exact migration/grant and denial evidence, including append-only support events and cross-database
  isolation;
- regressions proving CB-080/081/082 and CB-118 behavior remains unchanged and that no CB-123 or
  later capability was implemented;
- complete-diff self-review, fresh independent read-only review, final-head CI, the unique closeout
  `make ci`, and factual completion evidence.
