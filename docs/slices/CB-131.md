## Goal

Add one bounded human-handoff flow in which `commerce-service` owns the authoritative ticket,
state transitions, SLA deadline, and Outbox truth, while `agent-service` stores only an authenticated
projection and moves the owned support session into or out of `HUMAN_PENDING`. An open
authoritative ticket plus `HUMAN_PENDING` blocks sensitive writes without turning the projection,
Broker delivery, model output, or delay message into ticket truth.

## In scope

- Add a commerce-owned handoff ticket with a unique ticket id, one server-derived idempotent request
  key per configured session/action boundary, owner/session/trace/evidence correlation, bounded
  reason/risk fields, optional evaluation sandbox, state/version, SLA due time, and immutable
  creation commitment.
- Implement the frozen ticket lifecycle
  `REQUESTED → QUEUED → ASSIGNED → ACCEPTED → CLOSED / EXPIRED` with explicit legal transitions.
  Creation, each state transition, SLA delay event, and their Outbox row commit in the same
  `commerce_db` transaction.
- Expose only the fixed Agent-OBO `POST /internal/handoffs` boundary. The server derives owner,
  support session, sandbox, scope, idempotency, and evidence correlation from authenticated context
  and durable evidence; the model or caller cannot choose SQL, state, assignee, deadline, owner, or
  implementation.
- Trigger handoff only from the frozen bounded policy inputs: explicit user request, repeated
  unresolved intent, sustained negative sentiment, or high risk. Low retrieval confidence alone
  remains clarification or denial and cannot create a ticket.
- Persist an agent-owned projection keyed by authoritative commerce ticket id and support session,
  plus controlled `handoff_packet` evidence. The projection is immutable/versioned evidence and
  never authorizes or advances a commerce ticket.
- Atomically associate projection evidence with the agent session transition to `HUMAN_PENDING`;
  replay and restart reconcile against the authoritative commerce ticket before publishing status.
  Leaving `HUMAN_PENDING` requires a confirmed terminal authoritative ticket and cannot be inferred
  from a missing projection or message.
- Enforce the open-ticket sensitive-write guard at the Agent action boundary: a session in
  `HUMAN_PENDING` whose authoritative ticket remains open cannot prepare or confirm sensitive
  actions. Read-only clarification/status behavior remains bounded and cannot execute commerce
  writes.
- Publish and consume the ticket/transition/SLA Outbox family through the existing RocketMQ
  boundary. Every delayed SLA delivery re-reads durable ticket state and version; duplicate, late,
  reordered, restarted, or response-lost delivery cannot regress or invent a transition.
- Carry exact evaluation sandbox context on every evaluation-reachable handoff/SLA event, register
  the carrier in the executable asynchronous inventory, and apply the introduction-point liveness
  guard before work and immediately before mutation. Inactive work converges to the documented
  idempotent owner-local disposition; unavailable or indeterminate liveness remains retryable.
- Add exact migrations, runtime grants, bounded public/internal schemas, server-only rejection
  attribution, and durable evidence without expanding the current service/language boundaries.

## Acceptance criteria

1. Only an exact Agent OBO with the fixed handoff scope, actor, audience, user subject, owned support
   session, time bounds, and matching evaluation sandbox can create or read the handoff result.
   Direct-user, wrong actor/type/scope, cross-user/session, forged body identity, or sandbox mismatch
   fails closed.
2. Ticket creation uses one complete canonical intent commitment and one server-derived idempotency
   key. Same intent returns the same complete ticket; changed reason/risk/session/evidence/sandbox
   conflicts without another ticket or Outbox row.
3. One applicable open ticket exists per configured session/action boundary. Missing, duplicate,
   contradictory, or malformed ticket/Outbox truth fails closed and cannot be treated as absence,
   replay success, or permission to create another ticket.
4. Every ticket transition is a conditional state/version update inside one transaction with its
   exact Outbox event. Illegal, stale, duplicate-conflicting, terminal-regressing, or caller-selected
   transitions reject without partial state or event changes.
5. The SLA due time is bounded and committed once. A delayed delivery re-reads the authoritative
   ticket and changes state only when the expected open state/version and due condition still hold;
   duplicate, early, late-after-close, reordered, and restarted deliveries are idempotent.
6. `agent-service` stores only a strict authenticated ticket projection and bounded
   `handoff_packet`. Wrong owner/session/trace/ticket/version, duplicate keys, unknown fields,
   oversized evidence, or contradictory commerce responses cannot create or update a projection.
7. Projection persistence and the session move to `HUMAN_PENDING` form one local `cs_db`
   transaction. Controlled failure at either write boundary leaves no partial mode/projection
   success; retry resolves the commerce ticket before making the local state visible.
8. `HUMAN_PENDING` is never ticket truth. A missing message/projection, model statement, Redis
   value, or local timeout cannot close a ticket or release the guard. Leaving the mode requires a
   validated terminal commerce ticket and an atomic local transition/evidence update.
9. While both the owned session is `HUMAN_PENDING` and its authoritative ticket is open, every
   sensitive prepare/confirm path rejects before a business mutation. Concurrent action/handoff,
   close/action, replay, response-loss, and restart interleavings cannot execute a sensitive write
   through the guard or leave a false terminal ticket result.
10. Ticket/SLA consumers classify only positively established durable outcomes as terminal.
    Integrity failure, liveness/dependency unavailability, timeout, and indeterminate observation
    remain retryable or explicitly unavailable and never become ACKed absence, denial, closure, or
    success.
11. Evaluation-reachable carriers are present in the executable async inventory and preserve exact
    sandbox identity. Completion before delivery, completion during work, redelivery, restart, and
    liveness outage prove no late ticket/projection/session mutation and no terminal disposition
    while truth is indeterminate.
12. MySQL and `cs_db` remain the respective ticket and projection truths. Exact grants prevent
    `agent_app` from reading or mutating commerce ticket/Outbox tables and prevent
    `commerce_app`/`auth_app` from mutating agent projection/session evidence.
13. Public/internal handoff responses are closed and bounded. Server-only reason codes distinguish
    concealment, intent conflict, durable inconsistency, authorization/liveness rejection,
    contention indeterminate, and dependency unavailability without entering public bodies.
14. No agent workstation, assignment UI, arbitrary queue routing, new sensitive action, direct
    human-agent messaging, failure-candidate export, web work, deployment, provider credential,
    trace authority, or performance claim is introduced.

## Rejection paths

- Reject wrong token mode/issuer/audience/actor/scope, cross-owner/session, forged correlation,
  caller-selected ticket identity/state/assignee/deadline, unsupported trigger, and low retrieval
  confidence used alone as a handoff trigger.
- Reject incomplete idempotency comparison, duplicate or contradictory open tickets, missing or
  extra Outbox truth, stale state/version, illegal transition, terminal regression, and any
  create/update performed outside the required commerce transaction.
- Reject projection or `handoff_packet` creation from malformed/oversized/untrusted commerce data,
  model text, hand-built messages, direct repository fixtures, cross-session evidence, or a ticket
  whose complete durable closure was not validated.
- Reject entering `HUMAN_PENDING` without durable projection truth, leaving it without a validated
  terminal authoritative ticket, public status before local commit, and replay that creates a
  second ticket or contradictory projection.
- Reject sensitive prepare/confirm while the open-ticket guard applies, guard checks based only on
  cache/projection/message state, and races that perform the business mutation before the
  authoritative ticket check has been established.
- Reject SLA or normal consumers that trust payload state without re-reading MySQL, ACK an
  indeterminate failure, regress a newer state, mutate after sandbox completion, or omit the
  introduction-point liveness guard and executable inventory update.
- Reject broad grants, direct cross-database access, generalized recovery scanners, agent-side
  ticket authority, new product behavior, and CB-132 or later implementation.

## Out of scope

- a full support-agent workstation, assignment/routing marketplace, staffing schedule, human reply
  channel, or customer-service UI;
- new sensitive actions, changes to CB-118 ActionReceipt truth, refund/payment behavior, or the
  confirmation grammar and receipt projection owned by CB-121;
- summary/prompt/PII/output-safety work owned by CB-130 and failure-candidate review/export owned by
  CB-132;
- arbitrary ticket search/reporting, destructive cleanup, generalized recovery scanning,
  cross-system CRM integration, and real human-provider connectivity;
- web, observability implementation, deployment, real-provider access, demo/fault scripts, and
  measured load/latency/quality.

## Required evidence

- exact OBO owner/session/scope/sandbox authorization, total concealment, complete canonical intent,
  same-intent replay, changed-intent conflict, and bounded input evidence with zero unauthorized
  effects;
- real MySQL uniqueness/cardinality/content reconciliation and transaction rollback evidence for
  ticket creation, every legal transition, SLA deadline/event, and matching Outbox truth;
- deterministic concurrency, response-loss, restart, duplicate/reordered/late delivery, and stale
  state/version evidence proving one authoritative ticket and monotonic lifecycle;
- real Broker delay evidence proving early delivery, due transition, close-before-delay, duplicate,
  restart, dependency outage, and re-read-before-mutation behavior;
- real legal-producer evaluation evidence for active delivery, completion before delivery,
  completion racing work before persistence, consumer restart, liveness outage/indeterminate retry,
  recovery, and idempotent inactive disposition; plus the updated executable CB-104 inventory;
- strict agent projection/`handoff_packet` decoder, atomic projection plus `HUMAN_PENDING`
  transaction, local rollback, concurrent replay, restart, and validated terminal exit evidence;
- cross-path race evidence for action-before-handoff, handoff-before-action, close-before-action,
  and replay after response loss proving the open-ticket sensitive-write guard and no second
  commerce action;
- producer-specific server-only attribution and fixed public response evidence for concealment,
  conflict, durable damage, authorization/liveness, indeterminate contention, and dependency
  unavailability;
- exact runtime grants and cross-database/unrelated-table denial for `commerce_app`, `agent_app`,
  and `auth_app`;
- regressions proving CB-080/081/082, CB-118/121, and CB-130 contracts remain unchanged and no
  failure export, web, deployment, provider, observability authority, or performance behavior was
  implemented early;
- complete-diff self-review, fresh independent read-only review, final-head CI, unique closeout
  `make ci`, and factual completion evidence.
