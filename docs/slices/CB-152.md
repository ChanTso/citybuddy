## Goal

Produce reproducible, environment-labelled quantitative portfolio evidence for verified paths in the
local Docker Compose topology: seckill throughput/concurrency correctness, ordinary chat/RAG and
PendingAction-prepare latency under a Mock LLM, retrieval quality, FAQ cache effectiveness, and the
first observed bottleneck. Make no claim about unimplemented or real-provider behavior.

## In scope

- Pin and document the machine/container resources, service/image revisions, configuration,
  dataset/fixture versions, warm-up, duration, concurrency, arrival model, sample counts, run order,
  cleanup, and raw/result artifact locations for every measurement.
- Use JMeter for seckill reservation/order load. Report achieved request rate/QPS, latency and error
  distribution, and authoritative concurrency correctness: quota/stock bounds, one-user-one-activity,
  reservation/order/ledger cardinality, idempotent replay, and no false durable-order claim. JMeter
  client results provide throughput and latency, while Commerce durable database/state reconciliation
  provides correctness; neither depends on CB-150 or Java server metrics.
- Use Locust with the deterministic Mock LLM for ordinary chat, RAG, and PendingAction prepare paths.
  Report P50/P95/P99 and throughput/error counts per named path, with complete test validity and
  without describing Mock LLM results as provider capacity or quality. Path-separated Locust client
  results are the authoritative latency measure; Agent operation metrics may only cross-check them.
- Evaluate RAG on a versioned public/synthetic labelled dataset and report HitRate@5 and MRR with the
  exact query set, relevance judgements, index/corpus version, scoring formula, empty/insufficient
  handling, and reproducible command. This calculation is offline and has no service-metrics
  dependency.
- Measure FAQ mapping/answer cache hit rates and Elasticsearch knowledge-search avoidance with exact
  eligible-request denominators and exact CB-150 Agent counters. Reconcile `cache_served` to an
  actual zero-Elasticsearch-search path and `elasticsearch_issued` to an actual logical Elasticsearch
  knowledge-search invocation. Report cold, warm, bypass, expiry, replay, unavailable, and invalid
  cases separately without treating cache or metrics as truth. Provider-attempt counters are
  diagnostic only and cannot construct a saving ratio. These are the only portfolio outputs that
  require CB-150 counters.
- Identify the first bottleneck using client latency/error and throughput, authoritative durable
  state, Docker/container CPU, memory and I/O observations, and Agent metrics. If the evidence cannot
  isolate one, report `indeterminate`; missing Java server metrics neither invalidates the run nor
  authorizes new instrumentation. Stop at evidence and do not implement an optimization or broaden
  the route in this slice.
- Publish concise portfolio results linked to raw machine-readable artifacts and commands. Label all
  results local/mock and separate correctness, latency, throughput, and retrieval-quality claims.
- Retain exactly five portfolio outputs: seckill QPS/concurrency correctness; Agent-path P99; RAG
  HitRate@5/MRR; FAQ mapping/answer hit rates; and Elasticsearch knowledge-search avoidance. Do not
  add a sixth output or replace the fifth with provider/model saving.

## Acceptance criteria

1. Every reported number is reproducible from retained raw artifacts and names environment, dataset,
   configuration, warm-up, measured duration, concurrency/load model, sample size, and code revision.
2. JMeter reports seckill QPS/throughput, latency distribution, errors, and authoritative post-run
   correctness. Over-allocation, duplicate durable orders/movements, owner leakage, stuck terminal
   work, or an unexplained error invalidates the performance run rather than becoming a footnote.
   Client results and Commerce durable truth are sufficient; Java server metrics are not required.
3. Locust reports path-separated ordinary-chat, RAG, and PendingAction-prepare P99 plus P50/P95,
   throughput, errors, and sample counts under the pinned Mock LLM. Mixed aggregates cannot replace
   the per-path results. Locust client latency is authoritative; Agent operation metrics are optional
   corroboration only.
4. HitRate@5 and MRR use the fixed labelled query/relevance dataset and documented formulas. Missing,
   duplicate, stale-version, unjudged, or malformed cases fail the evaluation or use an explicit
   predeclared denominator rule; they are never silently dropped and require no service metrics.
5. FAQ mapping hit rate and answer hit rate each use the exact CB-150 `hit / (hit + miss)` counters,
   and Elasticsearch knowledge-search avoidance uses
   `cache_served / (cache_served + elasticsearch_issued)`. Cold, warm, bypass, expiry, replay,
   unavailable, and invalid cases are reported separately. `cache_served` reconciles to zero actual
   Elasticsearch searches; `elasticsearch_issued` reconciles to an actual logical Elasticsearch
   knowledge-search invocation. Provider-attempt counters remain diagnostic and cannot enter or
   manufacture the ratio. No prediction, theoretical estimate, counterfactual baseline, replay,
   pre-choice denial or failure, retry, or provider fallback can add a backend decision; a logical
   Elasticsearch search that is invoked and then fails still records `elasticsearch_issued` exactly
   once. These are the only required CB-150 metric inputs.
6. The first bottleneck conclusion cites the earliest saturated/limiting resource or boundary and
   the supporting client, durable-state, container-resource, or Agent-metric evidence. If that
   evidence cannot isolate one, the result says `indeterminate` rather than guessing. Missing Auth
   or Commerce server metrics does not invalidate the run.
7. No result measures or claims Agent successful confirmation, Agent receipt Turn commit,
   MemoryPacker summary, handoff, or failure-candidate export. No local/mock result is presented as
   deployment, production, or real-provider performance/quality.
8. The repository retains executable commands, bounded datasets, raw machine-readable results,
   summarized evidence, and checks that fail when reports drift from artifacts.

## Rejection paths

- Reject unlabelled screenshots or prose-only numbers, discarded raw data, hand-edited aggregates,
  hidden failed samples, missing duration/dataset/environment, and incomparable mixed-path P99.
- Reject throughput runs without authoritative correctness reconciliation or with expired/invalid
  credentials and fixtures that accidentally produce the expected status.
- Reject RAG metrics without fixed judgements/formulas, FAQ or Elasticsearch-avoidance results
  without exact denominators and request/search-call reconciliation, and bottleneck claims based
  only on intuition.
- Reject reintroducing model-call saving, counting replay/denial as cache saving, estimating provider
  saving from cold/warm traffic, or deriving a saving ratio from provider-attempt differences or a
  counterfactual baseline without a real producer.
- Reject adding Auth or Commerce metrics, Micrometer, or Java scrape endpoints in CB-152; reject
  treating missing Java server metrics as a failed run or as authority to add instrumentation.
- Reject measurements or claims for Agent confirmation/receipt, MemoryPacker summary, handoff,
  candidate export, real providers, or production capacity.

## Out of scope

- performance optimization, autoscaling, deployment/SLO promises, real-provider benchmarking,
  multimodal work, recovery scanners, dashboards, new business behavior, or Auth/Commerce metrics;
- Agent successful confirmation, Agent ActionReceipt projection/turn commit, memory/PII, handoff,
  failure-candidate export, cart, full storefront, or workstation load.

## Required evidence

- versioned JMeter plans, raw results, environment manifest, and authoritative post-run seckill
  correctness reconciliation, with no Java-metrics dependency;
- versioned Locust/Mock-LLM scenarios and authoritative raw path-separated client
  latency/throughput/error results, with any Agent operation metrics labelled corroborative;
- versioned RAG dataset/judgements plus offline executable HitRate@5/MRR calculation and raw
  rankings, independent of service metrics;
- exact CB-150 Agent mapping/answer cache-layer counters and backend-decision counters across cold,
  warm, bypass, expiry, replay, unavailable, and invalid paths;
- real request-to-Elasticsearch-call reconciliation proving `cache_served` means zero searches and
  `elasticsearch_issued` means one actual logical knowledge-search invocation, with provider-attempt
  counters retained only as diagnostics and no model-saving claim;
- client, durable-state, Docker/container-resource, and Agent-metric evidence for the first
  bottleneck, or an explicit `indeterminate` conclusion when it cannot be uniquely identified;
- an executable guard that CB-152 introduces no Auth or Commerce metrics dependency or producer;
- artifact-to-report consistency checks, complete-diff self-review, fresh independent review, and
  final repository checks.
