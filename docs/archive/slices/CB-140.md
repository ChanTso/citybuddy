## Goal

Turn the verified CityBuddy paths into one minimal, runnable portfolio web demonstration and refresh
the README to describe only repository facts: login, product browsing, seckill reservation and
status polling, support chat, and the Agent-local PendingAction prepare/clarification/decline/expiry
boundary. Do not imply that Agent confirmation or receipt closure exists.

## In scope

- Replace the current web skeleton with one small responsive React/TypeScript surface that consumes
  only existing verified APIs. Keep navigation and state management local and reviewable; do not
  introduce a full commerce application architecture.
- Support direct-user login through the verified identity endpoint, explicit signed-out/expired-token
  handling, and authenticated calls without exposing credentials or trusting client-supplied owner
  identity.
- Show the verified published-product list and a seckill entry that submits one idempotent
  reservation request and polls its owner-scoped status through the CB-060 public routes. Render
  reservation truth exactly as returned and never equate `PENDING` or `ADMITTED` with a durable
  order or successful payment.
- Create and reuse an owned support session, submit support turns, and render the verified filtered
  SSE/public chat outcomes. Show bounded loading, empty, denial, unavailable, replay, and terminal
  states without exposing internal tool, retrieval, trace, or server-only evidence.
- Render a PendingAction card only from the verified CB-122 `action_pending`/`PREPARED` projection.
  The card may guide clarification and may submit a documented decline through the existing chat
  path; it must display the verified declined or expired local outcome. Expiry is derived from the
  server outcome/deadline, not a client-created business transition.
- Provide no successful confirmation control. If a confirmation-shaped input reaches the existing
  chat path, render the fixed typed CB-122 non-success exactly as unavailable and perform no local
  success projection.
- Refresh README facts, startup prerequisites, local startup and test commands, limitations, and a
  reproducible demonstration walk-through. Remove obsolete claims that the repository contains only
  skeletons or no business behavior, while making the still-minimal web surface and mock/local model
  boundary explicit.
- Add focused component, API-adapter, state-transition, accessibility, and build evidence for the
  web behavior, plus README command verification. Reuse existing schemas and endpoints; do not
  modify OpenAPI, production services, migrations, grants, or business truth.

## Acceptance criteria

1. A user can log in, sign out, recover from invalid/expired authentication, and reach authenticated
   product, reservation, and chat views without client-supplied ownership or leaked token material.
2. The product list represents only the existing published-product response and covers loading,
   empty, success, authorization, malformed-response, and dependency-unavailable states.
3. Seckill submission uses a stable request idempotency key and the verified public route. Polling is
   owner scoped, bounded/cancellable, and renders only the server reservation status; no UI copy or
   state claims order creation, payment, or inventory truth before the verified response does.
4. Support chat creates/reuses one owned session and renders only the CB-082 public event surface.
   Internal ToolSpec, OBO, retrieval, evidence, trace, and server-only rejection details never enter
   the DOM, browser log, or persisted client state.
5. A valid prepared action renders one bounded PendingAction card with the safe CB-122 projection.
   Clarification changes no action state; decline and expiry render their verified local terminal
   results and cannot create a receipt, completed turn, or commerce mutation.
6. No successful confirmation button or receipt card exists. Confirmation-shaped input displays the
   current fixed unavailable result; the UI never fabricates `refunded`, `executed`, `confirmed`,
   `action_completed`, `ActionReceipt`, or receipt status from prose, timing, optimistic state, or a
   client-side inference.
7. Authentication, request, SSE, polling, retry, abort, and unmount paths are deterministic and do
   not duplicate a reservation, support turn, decline, or terminal rendering after response loss or
   React remount.
8. Keyboard navigation, visible focus, semantic status announcements, readable contrast, and small
   and desktop layouts make the complete demonstration usable without adding a design-system lane.
9. README statements match executable repository truth and include prerequisites, startup, tests,
   limitations, and ordered demo steps. It explicitly excludes real-provider claims, deployment,
   Agent successful confirmation/receipt closure, memory/PII, handoff, failure export, cart, full
   storefront, and agent workstation.
10. Existing repository checks and focused web tests/build pass without production, migration,
    grant, OpenAPI, or test weakening outside this slice.

## Rejection paths

- Reject client-side owner/session substitution, credential persistence or logging, permissive
  response parsing, hidden cross-user reuse, and authentication errors presented as empty success.
- Reject unbounded polling/reconnect, duplicate POSTs caused by rerender, optimistic reservation or
  action success, and `ADMITTED` presented as an order/payment result.
- Reject rendering internal SSE events, model/tool/retrieval data, server-only reasons, raw errors,
  or prose classification as action truth.
- Reject any confirmation success control, receipt card, synthetic receipt/action event, completed
  action copy, or local state transition that implies the unimplemented CB-123 boundary.
- Reject README capability inflation, unverifiable commands, real-provider or deployment claims,
  and stale skeleton-only descriptions.

## Out of scope

- Agent successful confirmation, Agent ActionReceipt validation/projection, `ACTION_RECEIPT`,
  `action_completed`, receipt cards, or post-commerce receipt recovery;
- MemoryPacker summary/watermarks, prompt/PII policy, tiered output work, handoff tickets,
  `HUMAN_PENDING`, candidate export, or any CB-130/131/132 behavior;
- cart, checkout UI, a complete storefront, a human-agent workstation, admin UI, deployment,
  production provider integration, new APIs, schema/migration/grant changes, or measured performance.

## Required evidence

- focused web tests for login/logout/expiry, products, reservation idempotency and bounded polling,
  support-session/chat/SSE filtering, PendingAction preparation, clarification, decline, expiry, and
  fixed confirmation unavailability;
- negative UI evidence proving no receipt/success control or copy, no optimistic action/order truth,
  no internal event/detail leakage, and no duplicate mutations across retry/remount/abort;
- responsive and keyboard/accessibility evidence for the complete demo path;
- successful web format, lint, typecheck, unit test, and production build commands;
- a command-by-command README demonstration run against the documented local topology;
- complete-diff self-review, fresh independent review, and final repository checks.
