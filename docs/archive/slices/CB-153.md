## Goal

Produce independently publishable, path-separated Locust latency evidence for verified Agent paths
under a deterministic Mock LLM. Report client P50/P95/P99, throughput, errors, and sample count for
each path without claiming real-provider capacity or quality. CB-153 validity does not depend on
CB-154.

## In scope

### Fixed paths and Mock LLM

The workload has exactly three named paths: `ordinary_chat`, `rag_sufficient`, and
`pending_action_prepare`. Each path independently reports P50, P95, P99, RPS, error count/rate, and
sample count. A mixed aggregate may be diagnostic but cannot replace or construct a path result.
The Mock LLM response script, role-alias mapping, fixed/pinned latency distribution, and provider
call and retry counts are retained. Mock delay remains part of the measured local path and is
separately labelled; it is never presented as framework overhead, provider performance, or
real-provider capacity.

### Path-validity controls

Every measured sample carries only a sanitized case/path locator in committed raw data. The runtime
checker keeps private session/trace values in its restricted temporary directory, queries the
authoritative stores, emits sanitized scalar controls, and destroys the locators during cleanup.

```sql
-- P01 against cs_db.
SELECT t.state, t.outcome,
       SUM(e.event_type = 'USER_INPUT') AS user_inputs,
       SUM(e.event_type = 'ASSISTANT_RESPONSE') AS assistant_responses,
       SUM(e.event_type = 'TURN_COMPLETED') AS completed_events,
       SUM(e.event_type = 'RETRIEVAL_DECISION') AS retrieval_events,
       SUM(e.event_type = 'ACTION_PREPARED') AS action_events
FROM support_turn t JOIN support_event e ON e.turn_id = t.turn_id
WHERE t.trace_id = :ordinaryTrace
GROUP BY t.turn_id, t.state, t.outcome;
```

```sql
-- P02 against cs_db.
SELECT t.state, t.outcome, d.sufficiency_outcome, d.candidate_count, d.evidence_count,
       COUNT(e.evidence_id) AS evidence_rows,
       MIN(e.evidence_rank) AS first_rank, MAX(e.evidence_rank) AS last_rank
FROM support_turn t
JOIN retrieval_decision d ON d.turn_id = t.turn_id
LEFT JOIN retrieval_evidence e ON e.decision_id = d.decision_id
WHERE t.trace_id = :ragTrace
GROUP BY t.turn_id, t.state, t.outcome, d.decision_id, d.sufficiency_outcome,
         d.candidate_count, d.evidence_count;
```

```sql
-- P03a against commerce_db.
SELECT pending_action_id, action_type, argument_hash, user_subject, support_session_id,
       trace_id, turn_id, required_scope, sandbox_id, order_id, target_order_version,
       amount_minor, currency, state, expires_at
FROM pending_action WHERE pending_action_id = :pendingActionId;
```

```sql
-- P03b against cs_db.
SELECT r.pending_action_id, r.source_turn_id, r.source_trace_id, r.session_id,
       r.user_subject, r.sandbox_id, r.action_type, r.argument_commitment, r.order_id,
       r.target_version, r.amount_minor, r.currency, r.state, r.expires_at,
       t.outcome,
       SUM(e.event_type = 'ACTION_PREPARED') AS prepared_events
FROM pending_action_reference r
JOIN support_turn t ON t.turn_id = r.source_turn_id
JOIN support_event e ON e.turn_id = t.turn_id
WHERE r.pending_action_id = :pendingActionId
GROUP BY r.pending_action_id, r.source_turn_id, r.source_trace_id, r.session_id,
         r.user_subject, r.sandbox_id, r.action_type, r.argument_commitment, r.order_id,
         r.target_version, r.amount_minor, r.currency, r.state, r.expires_at, t.outcome;
```

```sql
-- P04a against commerce_db after the public request; both scalars must be zero.
SELECT SUM(state = 'CONSUMED') AS consumed_actions,
       (SELECT COUNT(*) FROM action_receipt
        WHERE pending_action_id = :pendingActionId) AS receipt_count
FROM pending_action WHERE pending_action_id = :pendingActionId;
```

```sql
-- P04b against cs_db immediately before and after the public request.
SELECT r.pending_action_id, r.source_turn_id, r.source_trace_id, r.session_id,
       r.user_subject, r.sandbox_id, r.argument_commitment, r.state, r.expires_at,
       r.resolved_at, r.resolution_turn_id, r.resolution_trace_id,
       (SELECT COUNT(*) FROM support_turn t
        WHERE t.session_id = r.session_id AND t.user_subject = r.user_subject) AS turn_count,
       (SELECT COUNT(*) FROM support_event e
        WHERE e.session_id = r.session_id AND e.user_subject = r.user_subject) AS event_count,
       (SELECT COUNT(*) FROM support_turn t
        WHERE t.session_id = r.session_id AND t.user_subject = r.user_subject
          AND t.outcome = 'action_completed') AS completed_action_turns,
       (SELECT COUNT(*) FROM support_event e
        WHERE e.session_id = r.session_id AND e.user_subject = r.user_subject
          AND e.event_type = 'ACTION_RECEIPT') AS receipt_events
FROM pending_action_reference r WHERE r.pending_action_id = :pendingActionId;
```

The P02 public checker compares citation `sourceId`, `chunkId`, `sourceVersion`, rank, title, and
excerpt to the persisted ordered evidence allowlist. The P03 checker compares the two rowsets
byte-for-byte after the documented field-name mapping, requires Commerce `required_scope =
'refund:create'`, and verifies exactly one `ACTION_PREPARED` event. P04 requires the public status
and complete JSON body to equal `409` and `{"detail":"Action confirmation unavailable"}`. Its P04b
before/after rowsets must each contain exactly one row and be byte-for-byte equal after the same
ordered UTF-8 length-prefix/null encoding; `state` remains `PENDING`, resolution fields remain null,
and `completed_action_turns = receipt_events = 0`. P04a must return both zeros. This proves the
fixed rejection creates no unrelated Agent mutation or Commerce confirmation/receipt effect.

### Ephemeral thin runner and result bundle

The single command uses the same fixed chain:

```text
make init-local ENV_FILE=<run-env>
make up ENV_FILE=<run-env> COMPOSE_PROJECT_NAME=<unique-run-project>
start only required application child processes
readiness -> Locust warm-up -> measurement -> path-validity reconciliation -> artifact write
stop owned child processes
make reset-local CONFIRM_RESET_LOCAL=1 \
  ENV_FILE=<run-env> COMPOSE_PROJECT_NAME=<unique-run-project>
exact residue checks
```

`make up` retains responsibility for local-env validation, RocketMQ store/init/probe, data services
and health, grants, and all three migrations. `make down` preserves volumes and `ENV_FILE` and cannot
be final cleanup. The command uses a unique project/env, restricted temporary credentials, and a
trap only for direct child processes; it has no cross-command state or resume. It proves exact
project containers/networks/volumes, owned children, generated env, and temporary secret residue are
zero/absent. It never prunes host-wide resources, touches the default project or user `.env`, uses
wildcards, recreates active-run/phase/PID/container state, generalized demo/reset/fault behavior,
`make demo-*`, or PR #75 code/schema. Cleanup failure cannot hide the first failure.

Publish `evidence/measurements/CB-153/manifest.json`, `result.json`, `checksums.sha256`, and `raw/`
with a 40 MiB uncompressed raw budget; reduce a predeclared workload rather than discard samples.
The manifest contains the common fields `schemaVersion`, `sliceId`, `codeRevision`, `environment`,
`machine`, `containerResources`, `fixtureOrDatasetVersion`, `tool`, `toolVersion`, `warmup`,
`measuredDuration`, `concurrencyOrWorkload`, `sampleCount`, `commands`, `artifactInventory`, and
`cleanupResult`, and no secret/token/key, raw identity, session/trace/turn/PendingAction id,
production URL, or mutable absolute temp path. `result.json` contains only per-path
P50/P95/P99/RPS, per-path errors and sample count, and path validity. Raw records are lossless,
sanitized, bounded, include failures, and reconstruct the result without screenshots or hand edits.
JSON readers reject duplicate keys, unknown fields, malformed values, and declared size/record-count
overflow before materializing the complete artifact set.

## Acceptance criteria

1. All three paths independently reconstruct P50/P95/P99, RPS, errors, and sample count from raw
   Locust data; no mixed aggregate substitutes for them.
2. P01-P04 pass mechanically for the measured fixture and public result. Any invalid path control
   invalidates that complete run and suppresses all latency claims.
3. The pinned deterministic Mock LLM script, latency, provider-call count, and retry count are
   retained, and every result is labelled local/mock rather than provider capacity or quality.
4. Every failure is retained and classified, sample totals equal the manifest, and exact residue
   checks pass after explicit `reset-local` cleanup.
   Direct-user tokens, support sessions, PendingActions, and every other time-bounded fixture remain
   valid through their final path assertion; expiry evidence uses a separate short-lived fixture.
5. CB-153 becomes independently eligible for Resume-ready candidate review after its own
   `VERIFIED`, raw reconstruction, independent `NO BLOCKER`, and exact-main check success; CB-154
   cannot rewrite or gate it.
6. After the first full evidence run, allow at most two scope-owned semantic recovery cycles, each
   consisting of unique evidence, minimum correction, targeted verification, and full
   evidence/review. Read-only preflight, attribution-only work, superseded CI, approved external
   infrastructure reruns, and denied-before-execution commands do not count. Failure after two
   cycles marks CB-153 `BLOCKED`; per-path raw samples/errors, no-mixed-aggregate, path validity, and
   residue zero cannot be reduced.

## Rejection paths

- Reject mixed P99, hidden or unclassified errors, unequal sample inventories, invalid path
  controls, model delay disguised as framework latency, real-provider claims, and residual
  resources.
- Reject a PendingAction prepare path that claims confirmation/receipt success, omits the Commerce
  authority/Agent-reference binding, or accepts public prose as durable truth.
- Reject persistent active-run state, generalized lifecycle/framework work, host-wide or wildcard
  cleanup, `make down` as final cleanup, PR #75 reuse, a new platform, or a third recovery lane.

## Out of scope

- JMeter, seckill QPS/correctness, offline RAG quality metrics, FAQ/cache metrics, Elasticsearch
  avoidance, first-bottleneck or final aggregation;
- real providers, optimization, new Agent or business behavior, successful confirmation/receipt,
  deployment, generalized demo/reset/fault tooling, or private-core work.

## Required evidence

- pinned Locust and deterministic Mock LLM inputs, path-separated lossless raw samples,
  manifest/result/checksums, exact P01-P04 control outputs, and residue proof under
  `evidence/measurements/CB-153/`;
- executable artifact/result drift checker, secret/private-data scan, complete-diff self-review,
  fresh independent review, final `make ci`, final-head PR checks, and exact-main checks.
