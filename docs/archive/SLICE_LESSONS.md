# Slice lessons

The full per-slice pitfall record kept during the 2026-07 to 2026-08 slice process, translated
into English. It records only factual pitfalls supported by merged pull-request, commit, or
test evidence, and each slice records an explicit `none` when its merged evidence contains no
substantive pitfall. It is not a route-status, contract, acceptance, test, or review source.

The findings worth reading on their own are collected in English in
[docs/LESSONS.md](../LESSONS.md); this file is the unabridged source behind them.

## CB-010 — MySQL migration and access foundation

- Symptom: MySQL requires an account granting a privilege to hold that privilege and `GRANT OPTION` itself. This cannot coexist with the original absolute statement that bootstrap must never have business-data capabilities.
- Evidence: [slice PR #6](https://github.com/ChanTso/citybuddy/pull/6), [approved contract correction PR #5](https://github.com/ChanTso/citybuddy/pull/5)
- Cause: MySQL's authorization model requires a grantor to hold the privilege being granted; an account entirely lacking that privilege cannot grant it.
- Resolution: Place grantable privileges in a non-default role, allow only a one-time grant job with a fixed manifest to explicitly activate and clear that role, and verify `activate_all_roles_on_login=OFF`, `CURRENT_ROLE()=NONE` before execution, and rejection before any grant changes on failure paths.
- Lesson: Database security boundaries must match the engine's actual authorization semantics. Short-lived, non-default roles and a fixed manifest can narrow the capability window; an impossible absolute description cannot.

## CB-012 — Elasticsearch and IK runtime foundation

- Symptom: The initial missing-IK rejection test injected the fault by modifying an existing container and restarting it. Linux Compose recreated the container, so the test might not have exercised the intended instance without IK, creating a false-green risk.
- Evidence: [slice PR #10](https://github.com/ChanTso/citybuddy/pull/10), [portable rejection commit `cefbe53`](https://github.com/ChanTso/citybuddy/commit/cefbe539b349f95131b366040967ca46e6cc88a8)
- Cause: Fault injection depended on Compose reusing a modified container, behavior that was not stable across platforms.
- Resolution: Start the official Elasticsearch image at the same digest in a separate fault project without installing IK, then verify the container digest, unhealthy state, plugin directory, and plugin inventory.
- Lesson: Infrastructure rejection tests should create a fault instance whose condition can be independently established, without depending on container-reuse implementation details.

## CB-013 — RocketMQ Broker and Proxy foundation

- Symptom: The draft interpreted one read with no duplicate after the probe's ACK as proof of single delivery. It also wired the RocketMQ standalone round trip into an aggregate target owned by the later CB-014 slice.
- Evidence: [slice PR #12](https://github.com/ChanTso/citybuddy/pull/12), [review correction commit `4ac2e60`](https://github.com/ChanTso/citybuddy/commit/4ac2e60a6ae425e4186f573c426c8e1085ae5c38)
- Cause: An ACK used for cleanup was expanded into proof of delivery semantics, while implementation crossed the current slice's boundary for aggregate wiring.
- Resolution: Limit the probe to proving that a uniquely identified message matches exactly once within one batch. Use ACK only for cleanup and remove the “ACKNOWLEDGED/secondDelivery” semantics; leave the aggregate target to CB-014.
- Lesson: A probe can claim only the behavior it actually observes. Cleanup is not proof of a reliability protocol, and orchestration owned by a later slice must not be implemented early.

## CB-014 — Aggregate runtime integration closure

- Symptom: Independent review found that the MySQL probe still inherited the default Redis host ports, risking conflicts with a developer's running topology. The README also omitted Docker Compose, OpenSSL, and `sha256sum`, which the full integration path actually required.
- Evidence: [slice PR #14](https://github.com/ChanTso/citybuddy/pull/14), [isolation and prerequisites commit `d8597cd`](https://github.com/ChanTso/citybuddy/commit/d8597cd4ddcf26a1a0eb80f3d04cec83662d0cbb)
- Cause: Aggregate tests introduced cross-component dependencies without extending port isolation and local-tool prerequisites to the complete topology.
- Resolution: Isolate the MySQL, Redis, Elasticsearch, and RocketMQ host ports used by the MySQL probe, complete the actual tool prerequisites, and rerun component, aggregate, and full CI checks.
- Lesson: An aggregate test's isolation and dependency inventory must cover every component it starts indirectly, beyond the primary component named by the test.

## CB-030 — Product catalog cache

- Symptom: After the Commerce `V002` migration was added, the aggregate runtime test still hardcoded one Commerce migration, causing the first full `make ci` run to fail.
- Evidence: [slice PR #17](https://github.com/ChanTso/citybuddy/pull/17)
- Cause: The test made the migration count, which grows with the repository, a constant instead of deriving its expectation from version-controlled migration files.
- Resolution: Calculate the expected migration count from checked-in `V*__*.sql` files, then rerun targeted runtime integration, independent review of the full diff, and full `make ci`.
- Lesson: Count assertions for enumerable repository assets should derive from the same authoritative asset set, avoiding maintenance failures when a valid file is added.

## CB-040 — Standard ordering and MySQL inventory

- Symptom: Real MySQL evidence exposed two design problems: the implementation initially needed an unauthorized migration `ALTER` to provide an additional inventory version, and the idempotency lock table used by `SELECT ... FOR UPDATE` lacked the exact `UPDATE` privilege MySQL actually required. Subsequent review also added stable malformed-body error mapping, route rejection for wrong issuer/audience/type, and idempotency-guard cardinality assertions.
- Evidence: [slice PR #22](https://github.com/ChanTso/citybuddy/pull/22), [closeout evidence](https://github.com/ChanTso/citybuddy/pull/22#issuecomment-4981130003)
- Cause: The initial design did not fully match the authoritative values available in the existing schema or MySQL's actual privilege semantics for locking reads. Some route and concurrency-guard rejection evidence was also insufficiently direct.
- Resolution: Use the authoritative stock value directly as the optimistic inventory version, grant the lock table the minimum required `UPDATE` privilege, and add error mapping, token rejection, and per-key/cardinality assertions before rerunning full CI.
- Lesson: Transaction design and least privilege must be validated against a real database. Framework behavior or the apparent meaning of SQL cannot substitute for the engine's actual privilege and locking behavior.

## CB-050 — Seckill activity allocation and versioned projection

- Symptom: Java `Instant` can carry nanosecond precision, while MySQL `TIMESTAMP(6)` retains only microseconds. Building the Redis projection from the unnormalized input after the initial write caused an existing-key rebuild to misclassify the same fact as a conflict.
- Evidence: [slice PR #23](https://github.com/ChanTso/citybuddy/pull/23)
- Cause: The Redis projection used the input precision from before persistence, while the authoritative MySQL fact had already been normalized to the column's precision. The two representations were no longer literally identical.
- Resolution: Read the authoritative MySQL fact again after commit before projecting it, and use sub-microsecond input to verify idempotent existing-key rebuilds.
- Lesson: Cross-store projections must be generated from the persisted authoritative representation, with explicit treatment of reductions in timestamp and numeric precision.

## CB-051 — Seckill reservation and atomic admission

- Symptom: Independent review found four gaps in admission/rebuild invariants, plus a risk that an oversized TTL could leave a partial write before failing.
- Evidence: [slice PR #24](https://github.com/ChanTso/citybuddy/pull/24)
- Cause: Lua atomicity does not automatically ensure the business integrity of input numbers, TTL limits, version relationships, or rebuild markers. With incomplete boundary validation, a script can still atomically write incorrect or partial state.
- Resolution: Complete identity/version/number/TTL and corrupt-marker validation. Reject unsafe CJSON integers, sub-millisecond/oversized TTLs, and partial/version-lag state before any write, then rerun integration and full CI against real Redis/MySQL.
- Lesson: An atomic script guarantees indivisible operations, not correct decisions. Every boundary that can affect the write set must be validated before the first mutation.

## CB-060 — RocketMQ transaction admission and seckill order creation

- Symptom: The Broker configured `transactionCheckMax=3`, but a real repeated-`UNKNOWN` drill observed only 2 checker callbacks. An attempt to gather evidence by subscribing from the application to `TRANS_CHECK_MAX_TIME_TOPIC` returned `40002 cannot access system topic` from RocketMQ Proxy. The application therefore could neither treat callback count as a termination protocol nor read the system termination topic through Proxy.
- Evidence: [slice PR #25](https://github.com/ChanTso/citybuddy/pull/25), [approved contract clarification `5edb73c`](https://github.com/ChanTso/citybuddy/commit/5edb73c009f570d9e68ef6e6e9efd2b6fe1e31b8), [deadline convergence `54999ee`](https://github.com/ChanTso/citybuddy/commit/54999ee03903455dc3e41a370489ca1f4d72cf4f), [checker evidence `750dfdf`](https://github.com/ChanTso/citybuddy/commit/750dfdf7097e129405896358063c6d64ab90d39d), [marker validation recovery `52939b0`](https://github.com/ChanTso/citybuddy/commit/52939b0d8af1a9d5dba62ea9f1cf5cf2b38faa02)
- Cause: The Broker did not expose its termination timing through a callback-count protocol the application could rely on, and Proxy prohibited application access to the system termination topic. Treating an observed count or message payload as durable truth would make restart and race outcomes unreliable.
- Resolution: Abandon two uncommitted recovery approaches: having the application consume the system topic, and terminating by counting checker callbacks/modifying the message payload. The final approach persisted a one-time `transaction_resolution_due_at` in MySQL, deriving its upper bound from the Broker check-window configuration plus a safety margin and never recalculating it on restart. An indexed worker processed expired `PENDING` rows in bounded batches of 32. Redis Lua CAS let the first valid admission/timeout decision win and write a durable marker, then converged MySQL idempotently. The checker returned to a pure mapping over a read-only marker, returning `UNKNOWN` when Redis was unreadable; independent `mqadmin` access to the system topic established the Broker's terminal state.
- Lesson: The configured `3` versus the observed `2` is a diagnostic difference only, never an application protocol. The application should determine its terminal state through its own durable deadline and durable CAS; the Broker's terminal state should be established through a separate administrative path. Separating those responsibilities allowed real tests to prove convergence for both admission/timeout race orders, restart after Redis success/MySQL failure, three crash windows, preservation of ADMITTED, and the absence of an order/ledger on timeout.

## CB-061 — Delayed unpaid cancellation and ledger restoration

- Symptom: The first real migration evidence showed that a terminal row without `decision_code` could still pass V007's compound `CHECK`. Later real delayed-message integration exposed an overly tight 2-second expiry window and showed that combining assertions about durable MySQL state and Redis projections could contaminate the next case. Full-diff self-review also found that restoring activity quota after cancellation did not mean the same user could order again. Independent review further found that replacing Redis absolutely with the current MySQL count would miss concurrent deductions where Redis was already durably ADMITTED but MySQL remained PENDING, potentially inflating the remaining quota.
- Evidence: [slice PR #27](https://github.com/ChanTso/citybuddy/pull/27), [implementation commit `ebdceab`](https://github.com/ChanTso/citybuddy/commit/ebdceab)
- Cause: MySQL does not reject a row when a `CHECK` expression evaluates to `UNKNOWN`; the compound condition did not explicitly require a non-null terminal decision. Asynchronous tests treated scheduling jitter as a precise clock and confused durable truth with a projection that could fail. Quota restoration and user uniqueness are separate invariants, and a durable Redis marker can temporarily lead MySQL state, so a MySQL snapshot cannot treat it as nonexistent.
- Resolution: Add explicit `decision_code IS NOT NULL` to the terminal-state constraint. Use a stable expiry margin, separate MySQL/Redis evidence, and verify full rollback under a controlled mid-transaction exception. Exclude CANCELLED reservations from allocated activity quota while still rebuilding the user marker. Each cancellation also persists its own projection version; after commit, Redis Lua performs an atomic incremental restoration only between adjacent versions, preserving deductions from concurrent admissions. Missing or nonadjacent versions fail instead of triggering an absolute overwrite, then converge through a full MySQL rebuild. Real tests cover both the durable-marker/MySQL-PENDING window and the window after MySQL commit but before the Redis transition.
- Lesson: Database constraints must express non-null prerequisites under SQL's three-valued logic. Asynchronous evidence must allow for real scheduling and separate authoritative state from projections. Restoring quota and retaining the fact that a one-time purchase entitlement has been used must be modeled separately; cross-store recovery must also preserve durable decisions that may lead MySQL.

## CB-070 — Idempotent mock payment, authenticated callback, and payment ledger transitions

- Symptom: When two identical callbacks entered transactions concurrently, the old implementation first performed a shared read on a callback unique key that did not yet exist or had just been written, then updated the same payment attempt. Both transactions held shared/gap locks and requested exclusive locks simultaneously, consistently producing error 1213 deadlocks in real MySQL integration and preventing reliable convergence of duplicate callbacks. Full-diff review also found that the callback wrapper included `DuplicateKeyException` in its two attempts, exceeding the exact boundary of retrying only 1213.
- Evidence: [slice PR #28](https://github.com/ChanTso/citybuddy/pull/28), [implementation and recovery commit `730c029`](https://github.com/ChanTso/citybuddy/commit/730c029370aab7a1871b1d06ac5db2e13d3fccd1), [exact retry and rejection evidence commit `d2eb96e`](https://github.com/ChanTso/citybuddy/commit/d2eb96ed8d12c1811238d458532359efb6baeb34)
- Cause: This was a classic S→X lock-upgrade cycle: transactions A and B first obtained compatible shared/gap locks, then each waited for the other to release its lock so it could upgrade to the exclusive lock needed for writing. InnoDB had to choose a victim to roll back. The shared read preceded the actual serialization point, making deadlock a routine contention path. Combining unique-constraint rejection and an InnoDB deadlock victim into a broad concurrency retry also hid their different error semantics.
- Resolution: Make the callback transaction's first step a `SELECT ... FOR UPDATE` on the payment attempt by its unique callback correlation, queuing callbacks for the same attempt at entry. Read immutable callback truth normally only after obtaining the exclusive lock, avoiding shared S locks followed by contention for X. Retain a fallback of at most two total attempts, but retry only a `CannotAcquireLockException` whose exception chain explicitly contains MySQL error 1213. After the victim transaction fully rolls back, a new transaction rereads committed callback/order/attempt/ledger truth and returns the same result. Do not retry error 1205; execute `DuplicateKeyException` only once and map it to a stable 409. Five real catalog runs each executed 20 rounds of concurrent duplicate callbacks; all 100 rounds passed. Controlled 1213 evidence proved exactly one retry and one payment ledger movement, while controlled 1205 and unique-key conflicts were both surfaced immediately after one invocation.
- Lesson: `FOR UPDATE` addresses this cause because it serializes contenders for the same business entity in the same exclusive-lock order before they read derived state, eliminating the common S→X upgrade cycle—not because it can never deadlock. A bounded retry for exact 1213 still has a role: real transactions can form rare lock cycles with other resources such as cancellation, and InnoDB victim rollback is a recoverable concurrency outcome. Retries must reread committed truth in a new transaction, remain bounded, avoid disguising other errors as deadlocks, and rely on unique keys and conditional updates to prevent a second ledger movement.

## CB-071 — Refund state machine and payment/refund reconciliation

- Symptom: In the first real MySQL integration run, two concurrent partial refunds queued on the same payment attempt, yet the later transaction still calculated reserved amounts from an old REPEATABLE READ snapshot, admitting both. After that was corrected, the old `(order_id, movement_type)` unique key rejected a second valid partial refund. Final independent review found a similar window: reconciliation could read an old PROCESSING refund and then wait for a concurrent success to commit; an ordinary ledger read after locking would misreport the newly committed valid movement as a contradiction.
- Evidence: [slice PR #29](https://github.com/ChanTso/citybuddy/pull/29), [implementation and integration recovery `e159f37`](https://github.com/ChanTso/citybuddy/commit/e159f3754e95), [reconciliation current-read recovery `b8a1964`](https://github.com/ChanTso/citybuddy/commit/b8a1964)
- Cause: InnoDB lock waits serialize access but do not automatically refresh a consistent snapshot established earlier in the transaction. Any later ordinary aggregate or ledger read may still see the historical view from before the wait. Separately, the payment-stage constraint of at most one movement of each kind per order was applied directly to refunds, although one payment permits multiple partial refunds and therefore has different cardinality.
- Resolution: After taking the payment/order locks, calculate reserved amounts by current-reading that attempt's refund rows with `SELECT ... FOR UPDATE` and summing the locked rows. Use `FOR SHARE` current reads consistently for payment/refund/timeout ledger queries after reconciliation locks. A controlled test established an old snapshot before reconciliation waited for a success transaction to commit, then still returned `CONSISTENT`. Replace the old unique key with a generated conditional singleton key: preserve per-order singleton behavior only for existing ordering, cancellation, and payment movements, and make refund movements unique by the stable `mock-refund:{refundId}` business-event key. Ten rounds of concurrent excessive refunds each admitted only one; two valid partial refunds could both succeed cumulatively, while the database still rejected a second `STANDARD_PAYMENT`.
- Lesson: `FOR UPDATE`/`FOR SHARE` means more than taking a lock: in InnoDB it also means reading the current committed version at locking time. Audit and explicitly choose current reads for every derived total or related fact after a lock wait, beyond fixing the first query. Database uniqueness must also express the actual cardinality of business events: payments may be singletons per order, while partial refunds must be singletons per stable refund identity. An overly broad legacy constraint cannot represent both.

## CB-080 — Support conversation, event, and evidence lifecycle

- Symptom: With four concurrent requests for the same intent, the draft first shared-read `support_session`, then contended for the conversation write lock. Real MySQL produced 1213 deadlocks and returned 503. Changing the session read directly to `FOR UPDATE` then failed because the least-privilege `agent_app` lacked `support_session.UPDATE`. The integration script also appeared to hang because a bare `wait` waited for long-running service processes, trigger-based fault injection required unauthorized `SUPER`, and full CI finally exposed that the grant job did not recognize the exact table combination of historical partial Commerce migrations plus the full CB-080 Agent migrations. Independent closeout review also found that cross-user requests locked the conversation before eventual rejection, and that the original rollback drill failed on the first event, never exercising full rollback after partial evidence writes.
- Evidence: [slice PR #31](https://github.com/ChanTso/citybuddy/pull/31), [implementation commit `1645126`](https://github.com/ChanTso/citybuddy/commit/1645126), [review recovery `f4bfe43`](https://github.com/ChanTso/citybuddy/commit/f4bfe43)
- Cause: Transactions took compatible shared locks before upgrading to exclusive locks, forming the same S→X contention cycle as CB-070. Directly locking the session also confused reading the authoritative owner with holding update permission on that table. Test orchestration did not separate one-shot client PIDs from long-running service PIDs, and fault injection depended on administrative privileges the runtime identity should not hold. The upgrade state machine enumerated only the old Agent schema, without combining the new tables. The final in-transaction owner recheck was mistaken for an entry-time authorization precheck, and the fault constraint matched only the first event based on the input message.
- Resolution: Create the conversation when creating the session. At chat entry, validate the owner from `support_session`; inside the transaction, serialize on the conversation row with `SELECT ... FOR UPDATE` and reread the immutable session owner. Four concurrent requests then consistently converged to the same response, one turn, and three events. Have the script wait only for recorded curl PIDs. Use a migration-owned `CHECK` constraint to inject failure on the second event of a separate conversation with no history, proving that the first event, turn, and conversation position roll back together. Explicitly enumerate all seven historical Commerce states combined with the CB-080 Agent tables, continuing to fail closed for unknown table sets.
- Lesson: Concurrent idempotent transactions should serialize early on the same business aggregate root for which they hold write permission, then read related authoritative facts; do not expand unrelated table privileges merely to lock. Entry authorization order and an in-transaction TOCTOU recheck are separate defenses and cannot replace one another. Rollback evidence must also let at least one protected write execute successfully before a later write fails. Process waits, fault injection, and upgrade matrices in real integration must respect least privilege and precisely distinguish short tasks, resident services, and each supported schema combination.

## CB-081 — Bounded agent, model routing, and ToolSpec control

- Symptom: The first remote repository CI run classified two fixed, high-entropy `Idempotency-Key` test values in an integration script as generic API keys. Meanwhile, the real chain required an accepted turn to be saved before external model/identity/tool calls, but also required later database failure to leave no partial Agent evidence and not rerun tools for the same idempotent request. Independent review found that a process crash after committing `PROCESSING + USER_INPUT` would make that request return 409 forever; a half-open probe receiving a non-transient provider/schema rejection would also hold the default single probe slot forever. Full review after revision found that V004, while replacing the V003 constraint to add event types, accidentally retained only positive sequence numbers and the type allowlist, allowing a terminal event at sequence 1 or repeated `USER_INPUT` at later positions.
- Evidence: [slice PR #32](https://github.com/ChanTso/citybuddy/pull/32), [first failed CI run](https://github.com/ChanTso/citybuddy/actions/runs/29574307542), [fail-closed authority evidence `0c7db0c`](https://github.com/ChanTso/citybuddy/commit/0c7db0c), [crash/circuit review recovery `e24024f`](https://github.com/ChanTso/citybuddy/commit/e24024f), [final-migration invariant recovery `f23b9d2`](https://github.com/ChanTso/citybuddy/commit/f23b9d2)
- Cause: Secret scanning uses field-name and entropy heuristics and does not know that a string is merely a test correlation key. Holding a database transaction open across network calls provides no reliable atomicity and widens lock windows; one large transaction cannot express both acceptance and all-or-nothing evidence after external execution. The draft handled only exceptions in a still-live request stack and persisted no deadline for committed execution ownership. The circuit breaker cleared half-open state only on success or transient failure, omitting non-transient and unexpected-exception exits. At the migration layer, adding event types accidentally became wholesale constraint replacement, while static tests still proved only the old V003 text rather than the invariants after the final migration.
- Resolution: Replace the false positives with low-entropy test placeholders with clear meanings and remove the draft commit history containing them. Give turns two durable phases: first commit `PROCESSING`, `USER_INPUT`, and a one-time deadline derived from the bounded attempt budget; after external execution, commit complete Agent events and terminal state in one transaction. On controlled second-phase failure, roll back all partial Agent evidence, then use a separate bounded transaction to converge the same accepted turn to `FAILED`. Expired replay writes durable failure only once under the turn's exclusive lock, with completion fenced by the same deadline; it does not rerun the Agent or tools. Release the half-open probe slot in every admitted call's `finally`, while success and transient failure still perform their respective state transitions. V004 explicitly preserves `sequence = 1 ⇔ USER_INPUT` while extending the allowlist. New static assertions and real `agent_app` write rejections prove both that a terminal event cannot precede input and that input cannot repeat at later sequence positions.
- Lesson: Design test identifiers with secret-scanning rules in mind. Durable workflows involving network I/O should explicitly separate acceptance from completion and give execution ownership a durable, fenceable termination boundary after a process disappears. Bounded circuit breaking requires auditing all release paths—success, transient, non-transient, and unexpected exceptions—as well as limiting probe admission. When incremental migrations change existing constraints, tests must target the final migration definition and real database behavior, beyond proving the historical DDL being replaced.

## CB-082 — Filtered SSE, feedback, and deterministic support end-to-end evidence

- Symptom: The first real MySQL migration failed because the support-turn columns referenced by the feedback foreign key had no explicit composite unique key. After correction, a feedback transaction's locking read was rejected with 1142 under least-privilege `agent_app`. Real identity integration also found that the SSE route swallowed an owner `HTTPException` into a public error with HTTP 200, while a hardcoded event sequence in an old crash-window fixture collided with a new SSE turn. The action-success vocabulary approach failed two rounds of independent review: the first demonstrated a narrow-regex bypass with `Your cancellation is complete.`; after normalization, review found `It has been refunded.` / `I cancelled it for you.` and a false rejection of `Your order is not complete.`; after the second correction, review still found `Your refund has been issued.` / `The payment went through.` and a false rejection of `No refund was processed.`. Full CI during closeout also reported Elasticsearch unhealthy twice, although live health records showed consecutive successes and `FailingStreak=0` before the container suddenly reached 0 PIDs and was removed.
- Evidence: [slice PR #33](https://github.com/ChanTso/citybuddy/pull/33), [implementation and integration recovery `63103c8`](https://github.com/ChanTso/citybuddy/commit/63103c8), [first action-claim review recovery `e07d867`](https://github.com/ChanTso/citybuddy/commit/e07d867), [completed-action/negation recovery `44a83a1`](https://github.com/ChanTso/citybuddy/commit/44a83a1), [authoritative-channel decision `d796ac7`](https://github.com/ChanTso/citybuddy/commit/d796ac7), [bounded defense recovery `26eb851`](https://github.com/ChanTso/citybuddy/commit/26eb851)
- Cause: MySQL foreign keys recognize explicit indexed uniqueness of the referenced columns, and InnoDB locking reads require `UPDATE` on the target table. The route's exception boundary confused validated authorization rejection with private in-stream failure, while the historical fixture treated a growing sequence as a constant. For output filtering, a finite deterministic vocabulary cannot completely classify the synonyms, word order, tense, negation scope, and context of unrestricted natural language. Adding one phrase leaves new bypasses or introduces new false positives, so this cannot guarantee action truth. CI infrastructure problems arose because the shared Docker Desktop VM had only 7.75 GiB allocated at the time, with another unrelated project's container also resident. Resource pressure could make the largest JVM process disappear first while leaving only an apparently arbitrary component health-check failure.
- Resolution: Add an explicit composite unique key for support turns. Serialize concurrent feedback by locking only the `support_conversation` aggregate root, where write permission already exists, then read immutable truth. Preserve actual `HTTPException` responses in SSE and derive historical sequences from authoritative database state. The Level 3 revision completely separated the truth channel from prose: `token` is non-authoritative explanation, and the only public action-state carrier is `action_receipt` derived from ActionReceipt; subsequent clients must not infer state from prose. Normalization plus a documented bounded vocabulary serves only as defense in depth. Fixed regressions block `issued` / `went through` and allow `No refund was processed.`; a wire test proves that token prose cannot forge a second receipt SSE frame, and a real fake-provider run uses `Your refund has been issued.` as evidence. On the host, stop the unrelated containers and increase Docker memory to approximately 14 GB. A rerun collected 7,473 live `docker events`; full `make ci` passed with no `oom` events, without changing Compose, health checks, or slice code.
- Lesson: Design foreign keys, locks, and least privilege together against the real database. Separate HTTP authorization rejection from private in-stream errors, and derive sequences from authoritative state. A deterministic vocabulary cannot be claimed as a complete security boundary for free text. The correct structure separates the truth channel and demotes vocabulary checks to defense in depth: ActionReceipt/`action_receipt` determines state; `token` supplies only discardable explanation with no authorization power. Memory pressure in a shared Docker VM can masquerade as any component's health failure. Collect container events continuously during the run instead of relying on a post-run event buffer that can quickly be overwritten.

## CB-090 — Versioned hybrid knowledge index and deterministic retrieval fusion

- Symptom: The first real Elasticsearch bootstrap created an index and immediately classified it as `incompatible_mapping`. Actual 8.19.8 mapping readback retained `public_metadata.properties` but omitted that nested object's default `type: object`. ## CB-113 — Snapshot rebuild validation and atomic alias switch

- Symptom: Candidate indexes already required equality among owner-snapshot, Broker-journal, and `SYNC_EVENT` marker sets, but catch-up writes still used an Elasticsearch decoder that accepted duplicate JSON object keys and had no byte-collection bound. Independent review injected a valid old event already superseded by a newer owner version between the final marker validation and Broker ACK. Commit compared only the owner version, so it could ACK an event never included in the validated marker set. With multiple ACKs, if the first succeeded and a later one failed, Broker redelivery after restart contained only the suffix, while candidate-marker reconciliation misclassified the already-ACKed prefix as orphaned. The first recovery evidence separated second-ACK failure and union of sealed sets into two tests; both could remain green after deleting the coordinator's sealing/restart wiring. Candidate enumeration also collapsed two identical `SYNC_EVENT` hits into one map member. Review then constructed a two-coordinator interleaving: A paused after reading PREPARED control state without E; B sealed E and obtained an ACK checkpoint; A overwrote the whole document unconditionally with stale SWITCHED state, deleting E from the durable record. B could still ACK from its in-memory marker map, leaving the ACKed prefix unreconstructable after restart.
- Evidence: [slice PR #49](https://github.com/ChanTso/citybuddy/pull/49)
- Cause: Duplicate-key rejection and bounded reads existed only in the rebuild client, missing the catch-up client that reused incremental projection. Marker reconciliation committed only through in-memory validation arguments, without persistence before the first irreversible ACK. Broker per-message ACKs are not transactional; the Broker-visible set after failure cannot reconstruct a prefix already successfully disposed of. Even after adding durable descriptors, `seal_journal_events`, `prepare_switch`, and `complete_switch` each performed unconditional read-modify-write. Grow-only was a caller intention, not a storage guarantee. Unit tests separated by expected result established local properties, not that the production coordinator connected durable sealing, concurrent control-record updates, failure, process reconstruction, suffix redelivery, revalidation, and completion into one path.
- Resolution: Share a duplicate-key-rejecting decoder across every Elasticsearch JSON response boundary, rejecting oversized success/error responses while reading at a fixed limit plus one byte. For every record type, candidate classification rejects duplicate document IDs before map insertion. Before any ACK, the rebuild control record durably seals the exact journal-descriptor set sorted by event ID. Retain `_seq_no`/`_primary_term` when reading, create with `op_type=create`, and use version CAS for every update, with bounded reread and reevaluation against the latest record after conflict. Validate the immutable-subset relation for `journalEvents` before every write. Sealing returns the same immutable canonical `JournalCheckpoint` containing the complete descriptor tuple and deterministic marker map; pass it to both Broker commit and subsequent completion. For PREPARED and already SWITCHED records alike, completion checks expected-checkpoint containment by event ID/full contents and preserves the latest superset. Before ACK, commit prechecks all current pending events together: every owner-covered event must match all columns of a sealed marker. An old event arriving after validation fails consistently and remains unacknowledged. In the end-to-end recovery test, the coordinator writes a two-event checkpoint using production sealing. After deterministic failure of the second ACK, a new client retains only durable control state and candidate markers, and a new journal receives only the suffix. It must revalidate the complete two-member set before ACK and completion. A real Elasticsearch two-coordinator test forces A's stale completion write to interleave with B's new seal, proving A's CAS conflict, reread, superset preservation, and fresh-process reconstruction after ACK. Real runtime privilege evidence also proves that the `knowledge_indexer` MySQL account does not exist, that access to commerce/cs databases is denied, and that Support Redis rejects missing credentials, cross-prefix reads, and administrative commands.
- Lesson: Non-atomic external receipt disposition requires a durable commitment to the complete validated set before the first ACK. Otherwise, events arriving between validation and ACK and partially ACKed prefixes escape set reconciliation. Recovery cannot depend only on a suffix still eligible for redelivery; successfully ACKed members must also be reconstructable from a local durable checkpoint. Without storage-level version CAS, grow-only is merely a wish vulnerable to stale whole-document overwrites. Creation, sealing, preparation, and completion must consistently use create-only/CAS, rereading and reevaluating on conflict instead of resubmitting stale documents. ACK and completion must share the same immutable checkpoint with complete descriptors rather than deriving separate digests or in-memory marker maps. Audit parsing boundaries individually along shared call chains: fixing one client does not establish that every Elasticsearch response rejects duplicate keys or is bounded before collection. Separate local-property tests cannot replace production-wiring evidence across restart. If removing critical wiring leaves every test green, the evidence is false green.

## Defect correction — Reservation idempotency gap lock and insert-intention deadlock

- Symptom: Single-activity load tests never deadlocked, but spreading the same load ladder across 32 activity rows caused HTTP 500 responses from 400 req/s onward. One run accumulated approximately 6,200 `Deadlock found when trying to get lock` errors, all at `INSERT INTO seckill_reservation`. `SHOW ENGINE INNODB STATUS` showed both transactions holding X gap locks on the `supremum` pseudo-record of `uq_seckill_reservation_idempotency`, then each waiting for an insert-intention lock on the same gap.
- Cause: Before insertion, `reserveIntent` queried a row that **did not yet exist** with `SELECT ... WHERE user_subject=? AND activity_id=? AND idempotency_key=? FOR UPDATE`. InnoDB locks the gap rather than a record for an absent row, and gap locks are mutually compatible, allowing all concurrent transactions to hold them together. The subsequent `INSERT` needs an insert-intention lock on that gap, which conflicts with the other transactions' gap locks and creates a cycle. This did not occur for one activity because `seckill_activity ... FOR UPDATE` at transaction entry completely serialized contenders for that activity: only one could enter the insertion section at a time. **The row lock limiting throughput was also hiding this deadlock.**
- Resolution: Insert first and let the unique key decide replay. A successful `INSERT` creates the reservation. On `DuplicateKeyException`, use a `FOR SHARE` current read to fetch the existing row and compare `intent_hash`. This must be a current read because the REPEATABLE READ snapshot predates the concurrent insertion responsible for the duplicate; an ordinary read cannot see that row, the same class as CB-071. It must be `FOR SHARE`, not `FOR UPDATE`, because InnoDB already holds a shared lock on the duplicate record after a duplicate-key `INSERT`; upgrading to exclusive would recreate CB-070's S→X cycle. Regression evidence: 12 activities × 4 concurrent-reservation rounds consistently reproduced deadlocks before the fix and all reached ADMITTED afterward. With 32 activities, the same ladder improved from 26.67% failures and approximately 6,200 deadlocks to 0.00% failures and 0 deadlocks, sustaining the full 800 req/s.
- Lesson: A locking read for a possibly absent row and subsequent insertion of that key are inherently conflicting: the lock covers a gap, not a row. Unique constraints should adjudicate idempotent writes instead of a read-before-insert check. Read-before-insert is safe only when a broader lock completely serializes it, and that incidental safety disappears as concurrency dimensions expand. Audit both that the duplicate branch uses a current read, so it can see the newly committed row, and that it does not upgrade an already-held shared lock to exclusive.

## Maintenance — CI time attribution and matrix sharding for the evaluation sandbox suite

- Symptom: The single `test-evaluation-sandbox-integration` job took 46.0 minutes, compared with 7.9 minutes for the next slowest job, determining the entire CI critical path; 45.8 minutes fell within one step. - Cause: Computing differences between successive log timestamps showed that gaps of ≥5 seconds totaled only 2.9 minutes. The largest was exactly the 60-second expiry wait, while each Spring Boot restart took only 5–10 seconds. The real time was spread evenly across 23,372 log lines: evaluation and production physical-column corruption matrices totaled 3,080 cells, each performing one MySQL mutation, one classification probe, and one full truth restoration, totaling 39.9 minutes or 87%. What stood out structurally was not what consumed the time.
- Resolution: Every matrix cell ends with `restore_complete_*_payment_truth`, removing ordering dependencies between cells and allowing parallel partitioning. Introduce `SANDBOX_PAYMENT_MATRIX_SHARDS` / `SANDBOX_PAYMENT_MATRIX_SHARD`, sharding only mutation, probe, and restoration by global ordinal modulo. Leave pure metadata classification and cell counting unsharded, so every shard still asserts the complete 3,080-cell census and all totals 1541/1/1539/1/1485. - Lesson: Measure before attributing slowness; conspicuous waits are not necessarily the main cost. Evenly distributed overhead produces no log spikes and appears only through line-by-line accumulation. Parallelization requires state neutrality, provided here by every cell's restoration step. Sharding correctness should rest on a complete census assertion executed by every shard, not trust that partitioning is correct. Omitting a cell must fail the total-count assertion instead of silently running one fewer case.
