# Single-hotspot 160/s order work point, independently measured after restart

CityBuddy commit: `76c293178923bf78e747ab1ba9590e6348108ad8`. Local Apple M4, Docker configured for 8 CPUs / 14 GB (actual visible 14,638,391,296 bytes), Commerce 4 CPUs; k6 and services share the Docker network. One activity/SKU with 48050 users, stock and quota; 160 new requests/s for 300 seconds, without positive business warm-up. Measured HTTP ran approximately 2026-09-07 12:53:39–12:58:39 UTC. Complete parameters and JAR digests are in the same-label setup artifacts.

- k6 issued 48001 requests, all fresh ADMITTED; HTTP failures, drops, interruptions and negative durations were zero. HTTP p50 was about 2.3 ms, p99 about 30.6 ms; these are not order-wait times.
- SQL confirmed 48001 unique orders, all UNPAID with timeout SENT. Missing or duplicate orders, ownership/quantity-binding errors and ledger errors were zero. Inventory 49 + 48001 created orders = initial 48050; creation stock/quota deduction ledgers each contain 48001 entries.
- Wait from reservation persistence to order creation: p50 88.312 ms, p95 4885.575 ms, p99 8657.248 ms, maximum 10751.453 ms, without negative values. Startup is retained; later low latency does not replace the full window.
- SQL output across five fixed complete-minute windows was 152.35, 167.0667, 160.15, 159.95 and 160.00 orders/s. The initial queue recovered and the final three minutes showed no sustained imbalance. A separate incomplete-minute tail contained 30 orders; 30/60 is not the final minute's capacity.
- Grouped by reservation minute, p99 was 9975.208, 6030.460, 233.488, 252.027 and 308.038 ms. Five-second sampling found a maximum of 613 unordered reservations and 16 pending dispatches; samples around 118/178/238/298 seconds contained 25/10/8/8 unordered reservations.
- The last HTTP completed at 12:58:39.089689 UTC. The first SQL sample confirming all 48001 orders created and dispatched ended within about 4.198 seconds. The prior nonempty sample was before input stopped, so the supported statement is that the first post-input 5-second sample confirmed drainage, with an observed upper bound about 4.2 seconds, not an exact 4.198-second drain duration.
- After the measured after-state, transaction-message consumer Diff/Inflight was zero and global Redis handoff ZCARD=0. Future cancellation after 15 unpaid minutes belongs to subsequent lifecycle cleanup, not the measured order result.

## Segmented native statistics and interpretation

MySQL retained the original 128 MiB buffer pool, 100 MiB redo, flush-at-commit=1 and sync-binlog=1. Alongside the original 5-second order observer, native SQL statistics were captured before input, around 120 and 240 seconds, at input end and after drainage; actual times are recorded separately. Cumulative counters were not reset. The following values subtract adjacent original snapshots rather than treating old after-only totals as this run's increments.

| Interval | Actual seconds | COMMIT count / mean ms | Buffer-pool physical-read increment | wait_free increment | Cumulative row-lock wait increment, ms |
|---|---:|---:|---:|---:|---:|
| before→during120 |125.118|37986 /1.121|114931|34|23509|
| during120→during240 |120.102|38461 /1.005|210804|121|22172|
| during240→input_end |66.035|19612 /1.043|150510|104|12157|

Activity FOR SHARE averaged about 0.85–0.92 ms per interval (0.913 in the first), and FOR UPDATE about 0.38–0.40 ms, without sustained late deterioration. log_waits increments were zero in every interval. Growing physical reads and wait_free indicate buffer-pool/I/O pressure, but this point did not lose the ability to follow input; they do not establish a unique bottleneck or a need to scale resources. During the measured interval, Commerce cgroup throttling increased by 1 event / 14085 microseconds. Throttling was not entirely absent, but this is insufficient to establish sustained CPU saturation.

Conclusion at that time: a completed, SQL-correct 160/s, 5-minute work point, not yet repeated on this version and not a proven limit. Unlike the older DDE point, it did not show late backlog growth, but restart, environment state and observation methods changed. PR163 only adjusted cancellation-consumer pacing, so this does not prove an order bottleneck was fixed. The next step retained the same version and observation to test a repeat/higher load; this point did not justify a necessary code optimization.

Originals in this directory: `ladder_a160r2_76c2931_20260907T125104Z_steps.txt`, `k6_*`, `orders_*_{before,after,progress,resources}.txt`, `native_a160r2_*` and `mq_a160r2_*_ordered_*`, all retaining the full measured SHA. k6 points are the original JSON point stream.

After saving the measured result, the entire CityBuddy topology was paused, retaining volumes and unpaid orders, to give ShopMate an exclusive environment. The remote model remained in cooldown, so the original CityBuddy services were restored. This downtime occurred after measurement. Natural cancellation, inventory recovery and the final timeout-MQ state were to be saved as separate raw SQL; restart recovery speed is not a controlled performance comparison.

Subsequent recovery completed: full SQL at 13:30 UTC confirmed all 48001 orders CANCELLED, inventory 48050, 48001 creation/cancellation ledger entries each, and zero bad bindings, incomplete reservations or pending dispatches. See `recovery_a160r2_76c2931_final_1788787835587922000.txt`; both MQ groups had Diff/Inflight=0 in `recovery_mq_a160r2_76c2931_20260907T125104Z_1788787855249384000.txt`. The final Redis query after cancellation failed for missing authentication, so that query did not establish zero. The existing global-handoff guard later passed in the new a160r3 setup. This recovery included a pause and is not a controlled cancellation-performance comparison.
